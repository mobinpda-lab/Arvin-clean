# نقشه راه فعلی پروژه آروین — نسخه 1.1.0

> این سند از ۱۴۰۵/۰۵/۲۳ به بعد مرجع اجرایی وضعیت UI، پیگیری‌ها، CI و نسخه‌گذاری است. تغییرات جدید باید هم‌زمان با کد در همین سند ثبت شوند.

## 1. وضعیت مبنا

- مخزن: `mobinpda-lab/Arvin-clean`
- شاخه مبنا: `main`
- شاخه کاری این مرحله: `feat/arvin-v1.1-foundation`
- نسخه محصول هدف: **1.1.0**
- نام APK استاندارد: **`Arvin-v1.1.0.apk`**
- فناوری: Flutter / Dart / Android

## 2. یافته‌های بررسی آخرین مخزن

در وضعیت فعلی، مدل `ArvinTask` شامل عنوان، توضیح، تاریخ پیگیری، برچسب، بایگانی، سطل زباله و انجام‌شدن است؛ اما «پیگیری» هنوز به‌صورت تاریخچه چندرکوردی مدل نشده است. در نتیجه UI فعلی فقط یک `followUpDate` دارد و چیزی مانند «آخرین پیگیری + ساعت» در فهرست اصلی ثبت و نمایش نمی‌دهد.

همچنین UI فعلی از ChoiceChipهای «فعال / بایگانی / سطل زباله» استفاده می‌کند. طراحی هدف جدید باید این سه مورد را به‌صورت مقصدهای اصلی منو/ناوبری و آیکون‌های قابل کلیک ارائه کند، نه به شکل فیلترهای اصلی صفحه.

## 3. الزامات ثبت‌شده از تست کاربر

- تقویم باید **شمسی** باشد و ساعت را نیز در رویداد/یادآوری پشتیبانی کند.
- «پیگیری» یک وضعیت مستقل مانند فعال/بایگانی/سطل زباله نیست؛ پیگیری باید **تاریخچه‌ای از اقدامات** روی هر کار باشد.
- در لیست کارها باید **آخرین پیگیری و ساعت آن** نمایش داده شود.
- هنگام حذف، قبل از انتقال به سطل زباله باید **تأیید کاربر** گرفته شود.
- بازگردانی از سطل زباله باید کار را به حالت فعال برگرداند.
- بازگردانی از بایگانی باید ممکن باشد.
- کشیدن کار به سمت زباله باید با منطق حذف کنترل‌شده و قابل بازگشت کار کند.
- بایگانی و سطل زباله باید از طریق منوی برنامه/آیکون‌های اصلی قابل ورود باشند، نه صرفاً ChoiceChip.
- منوی اصلی برنامه باید در دسترس و مطابق طرح مرجع باشد.
- تنظیمات باید شامل گزینه **تغییر فونت** باشد.
- فونت‌های فارسی که قبلاً برای پروژه ارائه شده‌اند باید در طراحی نهایی دوباره استفاده شوند؛ قبل از تغییر نهایی فونت، فایل‌های فونت موجود بررسی و به assets پروژه متصل می‌شوند.

## 4. مرجع «دفتر پیگیری»

پروژه `mobinpda-lab/daftar-peygiri` به‌عنوان مرجع رفتاری برای تاریخچه پیگیری استفاده می‌شود، نه به‌عنوان جایگزین معماری آروین.

الگوی مفید مشاهده‌شده در آن پروژه:

- جدول/مجموعه `history` با ارتباط به `task_id`
- ثبت تاریخ و ساعت پیگیری
- شرح پیگیری
- نتیجه
- پیگیری بعدی
- نمایش آخرین پیگیری از جدیدترین رکورد تاریخچه
- امکان مشاهده تاریخچه کامل هر کار

این الگو باید در مدل فعلی آروین با migration سازگار پیاده‌سازی شود و داده‌های فعلی `ArvinTask` از بین نروند.

## 5. ترتیب اجرای نسخه 1.1.0

### فاز A — سلامت CI و نسخه‌گذاری

- اصلاح خطای `invalid_override` در تست Backup.
- تثبیت نسخه `1.1.0`.
- نام‌گذاری خودکار APK بر اساس نسخه: `Arvin-v<version>.apk`.
- حفظ ترتیب Analyze → Test → Release APK در CI.

### فاز B — هسته پیگیری

- افزودن مدل تاریخچه پیگیری با `dateTime` و فیلدهای شرح/نتیجه/پیگیری بعدی.
- backward-compatible کردن JSON فعلی.
- نمایش آخرین پیگیری + ساعت در کارت فهرست.
- صفحه/دیالوگ تاریخچه کامل پیگیری.
- تست واحد و widget برای ثبت، بازیابی و نمایش آخرین پیگیری.

### فاز C — چرخه وضعیت کار

- فعال، بایگانی و سطل زباله به‌عنوان مقصدهای ناوبری.
- بازگردانی مستقل از بایگانی.
- بازگردانی از سطل زباله به فعال.
- تأیید قبل از حذف.
- حذف دائمی فقط از داخل سطل زباله و با تأیید مجدد.
- تست drag-to-trash و restore.

### فاز D — منو و تنظیمات

- منوی اصلی مطابق طرح مرجع.
- مقصدهای: همه کارها، امروز، فردا، این هفته، انجام‌شده، برچسب‌ها، آرشیو، سطل زباله، پشتیبان‌گیری، تنظیمات، درباره برنامه.
- تنظیمات پایه شامل تم، زبان/تقویم و **تغییر فونت**.

### فاز E — تقویم

- ادامه کار از PR شماره 6 برای تثبیت انتخاب روز و layout.
- تبدیل تجربه تقویم به تقویم شمسی محصولی.
- پشتیبانی از ساعت یادآوری.
- اتصال رویدادهای تقویم به تاریخچه/پیگیری و reminderهای کار.

## 6. وضعیت CI که باید مبنا قرار گیرد

آخرین اجرای بررسی‌شده `Arvin Build #123` روی commit `c32106b` به دلیل خطای Analyzer متوقف شده بود؛ خطا مربوط به override تست `_FakeBackupService.writeBackup` بود که `uploadToCloud` را اجباری تعریف کرده بود، در حالی که قرارداد سرویس آن را اختیاری تعریف می‌کند. بنابراین Test و Build در آن اجرا اصلاً شروع نشدند.

این خطا در شاخه نسخه 1.1.0 اصلاح شده است و پس از اجرای PR باید Analyze، Test و سپس Build دوباره تأیید شوند.

## 7. قرارداد APK

از این مرحله به بعد نام فایل Release قابل تست باید دقیقاً از نسخه `pubspec.yaml` ساخته شود:

`Arvin-v1.1.0.apk`

در نسخه بعد فقط عدد نسخه تغییر می‌کند؛ ساختار نام ثابت می‌ماند:

`Arvin-v<version>.apk`

## 8. قانون ادامه توسعه

هر مرحله توسعه باید سه خروجی موازی داشته باشد:

1. تغییر کد و تست.
2. اجرای CI و تولید APK نسخه‌دار.
3. ثبت همان تغییر در مستندات پروژه.

تا وقتی کاربر APK را تست می‌کند، توسعه بخش‌های مستقل مانند مدل پیگیری، منو/ناوبری، تنظیمات فونت و تست‌های regression متوقف نمی‌شود؛ اما تغییرات پرریسک UI باید در شاخه‌های جدا و قابل بازگشت انجام شوند.
