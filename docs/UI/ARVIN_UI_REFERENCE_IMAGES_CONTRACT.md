# مرجع بصری قطعی آروین — تصاویر مرجع محصول

> وضعیت: **مرجع محصول / Product UI Authority**
>
> تاریخ ثبت: **۲۵ سپتامبر ۲۰۲۶**
>
> این سند در کنار `ARVIN_UI_CANONICAL.md` قرار دارد و جزئیات بصری تأکیدشده توسط مالک محصول را ثبت می‌کند.

## 1. اصل قطعی

تصاویر مرجع ارائه‌شده برای آروین، **مرجع بصری دقیق محصول** هستند؛ نه نمونه، پیشنهاد یا طرح موقت.

بنابراین در هر تغییر UI:

- رنگ‌بندی باید با تصاویر مرجع منطبق بماند.
- سبک و خانواده آیکون‌ها باید با تصاویر مرجع منطبق بماند.
- شکل کارت‌ها، حاشیه‌ها، گوشه‌ها، فاصله‌ها، تراکم و چیدمان RTL باید با تصاویر مرجع منطبق بماند.
- Home جدید و چهار نمای اصلی آن باید بر اساس همین زبان بصری پیاده‌سازی شوند.
- فرم «کار پیگیری‌دار / جزئیات کار» نیز **دقیقاً از الگوی تصویر مرجع مربوط به خود پیروی می‌کند**.
- هیچ UI قدیمی یا Home قدیمی مجاز نیست این مرجع را بازنویسی یا جایگزین کند.

## 2. چهار نمای اصلی Home

چهار نمای ثابت و اصلی:

1. **نمای زمان**
2. **نمای پروژه‌ها**
3. **نمای دسته‌ها**
4. **نمای برچسب‌ها**

تغییر نمای فعال باید فقط محتوای همان نمای را تغییر دهد و زبان بصری مشترک تصاویر مرجع حفظ شود.

## 3. زبان بصری مشترک

### هویت

- RTL و فارسی.
- عنوان محصول: **مدیریت کارها و پیگیری آروین**
- فونت محصول: **VazirHarf v34.003**
- بدون Device Frame یا Mockup به‌عنوان بخشی از UI واقعی محصول.

### رنگ

پالت ثبت‌شده در قرارداد اصلی UI همچنان مرجع است:

- Primary: `#4A4CAB`
- Primary Light: `#E9EAFF`
- Background: `#F8F8FB`
- Surface: `#FDFDFE`
- Text: `#232433`
- Secondary Text/Icon: `#80829C`

رنگ‌های فرعی مورد استفاده برای تمایز معنایی دسته‌ها/وضعیت‌ها باید در همان زبان بصری تصاویر مرجع باقی بمانند و نباید به یک تم رنگی مستقل تبدیل شوند.

## 4. Home جدید؛ ممنوعیت بازگشت به Home قدیمی

Home قدیمی **مرجع محصول نیست و نباید در Migration، Refactor یا Cleanup دوباره احیا شود.**

موارد زیر نباید به Home برگردند:

- کارت‌های قدیمی «کل / فعال / انجام‌شده / عقب‌افتاده»
- Dropdown قدیمی Home
- ساختار قدیمی گروه‌بندی
- ظاهر قدیمی کارت‌ها و کنترل‌ها
- رنگ‌بندی یا آیکون‌های متعلق به UI قدیمی
- Storage یا Model موازی برای پشتیبانی از UI قدیمی

اگر کد، تست یا وابستگی‌ای هنوز به Home قدیمی متکی است، آن وابستگی باید **اصلاح شود**؛ نه اینکه UI قدیمی دوباره وارد محصول شود.

## 5. نمای زمان

در نمای زمان، گروه‌بندی زمانی بر اساس **Task.dueDate** انجام می‌شود.

- Reminder و FollowUp به‌عنوان due date وارد گروه‌بندی زمان نمی‌شوند.
- ساختار گروه‌ها، رنگ‌ها، آیکون‌ها و کارت‌های Task باید با تصویر مرجع منطبق بماند.
- وضعیت‌ها و برچسب‌های معنایی باید همان زبان بصری مرجع را حفظ کنند.

## 6. نماهای پروژه، دسته و برچسب

هر سه نما باید همان ساختار بصری مشترک تصویر مرجع را حفظ کنند:

- نوار بالایی
- جستجو
- چهار دکمه نمای اصلی
- کنترل‌های مربوط به همان نما
- گروه‌ها
- شمارنده‌های داخل گروه‌ها در جایگاه بصری مشخص‌شده
- کارت‌های کار
- Bottom Navigation

تفاوت چهار نما باید **در داده و گروه‌بندی** باشد، نه در بازگشت به یک طراحی قدیمی یا ایجاد چهار زبان بصری جداگانه.

## 7. Bottom Navigation

ساختار مرجع:

**خانه | تقویم | دفترچه | اقدام بعدی | بیشتر**

ظاهر، ترتیب RTL، آیکون‌ها، حالت فعال و تراکم آن باید با تصاویر مرجع و قرارداد اصلی UI هم‌راستا باشد.

## 8. فرم «کار پیگیری‌دار» — مرجع دقیق

تصویر مرجع جزئیات «پیگیری قرارداد مشتری» یک **الگوی مستقیم محصول** است.

ساختار بصری مورد انتظار شامل:

- عنوان کار در بالای کارت اصلی
- وضعیت/نوع پیگیری
- پروژه و دسته‌های مرتبط
- توضیح کار
- تاریخ انجام
- یادآوری
- برچسب‌های معنایی مانند «مهم» و «مشتری»
- بخش مستقل **«آخرین پیگیری»**
- متن آخرین رویداد پیگیری و زمان آن
- بخش **«تاریخچه پیگیری»**
- نمایش رویدادهای پیگیری به‌صورت Timeline عمودی
- نقطه فعال/غیرفعال Timeline
- منوی هر رویداد
- دکمه اصلی **«افزودن پیگیری +»**
- دکمه **«انجام کار ✓»**

### رفتار معنایی

این صفحه فقط یک کارت Task نیست؛ باید ارتباط Task با FollowUp و تاریخچه FollowUp را به‌صورت یکپارچه و قابل فهم نمایش دهد.

**FollowUp نباید با Reminder یا Task.dueDate اشتباه گرفته شود.**

## 9. قواعد جلوگیری از Regression

قبل از Merge هر تغییر مرتبط با Home یا UI:

1. بررسی شود که Home قدیمی دوباره وارد مسیر اجرا نشده باشد.
2. بررسی شود که ظاهر چهار نمای مرجع تغییر ناخواسته نکرده باشد.
3. بررسی شود که فرم «کار پیگیری‌دار» از الگوی مرجع فاصله نگرفته باشد.
4. بررسی شود که رنگ‌ها و آیکون‌ها به قرارداد قدیمی برنگشته باشند.
5. بررسی شود که تغییر، Storage/Model موازی برای UI قدیمی ایجاد نکرده باشد.
6. در صورت تعارض بین کد قدیمی و این سند، **کد قدیمی قابل اصلاح است؛ این قرارداد مرجع محصول است.**

## 10. رابطه با Migration

Migration فقط وظیفه حفظ و انتقال داده واقعی کاربر را دارد.

- **داده واقعی کاربر: حفظ شود.**
- **شناسه‌ها و شمارش‌ها: حفظ شوند.**
- **Duplicate ایجاد نشود.**
- **Backup/Restore حفظ شود.**
- **Home قدیمی: مهاجرت نشود.**
- **وابستگی‌های Home قدیمی: شناسایی و اصلاح شوند.**
- **UI مقصد: همین قرارداد بصری باشد.**

هدف Migration، بازگرداندن ظاهر یا ساختار قدیمی نیست؛ هدف آن رساندن داده واقعی به معماری و UI نهایی آروین است.

## 11. اصل تصمیم‌گیری

اگر یک PR، Commit، تست یا Refactor با این مرجع تعارض داشت، قبل از Merge باید مشخص شود که آیا:

- آن بخش مربوط به داده/منطق قابل حفظ است؛ یا
- وابستگی قدیمی باید اصلاح شود؛ یا
- تغییر UI باید مطابق این مرجع بازطراحی شود.

**هیچ PR قدیمی صرفاً به دلیل قدیمی‌بودن یا وجود در تاریخچه، مجوز بازگرداندن Home یا ظاهر قدیمی را ندارد.**
