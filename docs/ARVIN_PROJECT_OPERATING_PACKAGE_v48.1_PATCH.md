## 49. EXECUTION DECISION MATRIX

- FAST CHANGE → Fast Path
- FEATURE CHANGE → Parallel Feature Execution
- FOUNDATION CHANGE → Controlled Path
- CRITICAL CHANGE (Sync, security, migration, breaking change) → Controlled Path + Architecture Review

Select the fastest safe execution path. Governance must not become a bottleneck.

## 50. STANDARD WORKSTREAM TEMPLATE

Every parallel workstream defines: Workstream ID, Objective, Scope, Owner/Agent, Input, Output, Dependency, Target Branch, Validation, Evidence, Integration Point and Status.

Lifecycle: Definition → Dependency Check → Assignment → Parallel Execution → Validation → Evidence → Integration → Documentation → Completion.

Workstreams should be independently executable where possible, with explicit boundaries and integration points.

## 51. PARALLEL CONFLICT PREVENTION PROTOCOL

Parallel execution is encouraged; parallel conflict is forbidden.

Before execution check file ownership, architecture boundary ownership, shared component usage, database/schema/migration impact, sync contract impact, duplicate implementation risk, active branches and PRs.

Conflict process: Detect → Classify → Assign Owner → Resolve → Validate → Document.

Multiple AI agents may work concurrently only with explicit Scope, Output, Boundary, Dependency and Validation.

## 52. AI EXECUTION CONTROL LOOP

Observe → Audit → Understand → Decompose → Parallelize → Execute → Fast Feedback → Evidence → Integrate → Document.

AI must establish Repository Reality, Existing Capability, Dependencies, Risks, Validation and Evidence requirements before acting. AI must never guess repository state, claim unverified success, duplicate existing capability, alter Foundation without audit, fabricate evidence, or hide conflicts.

Success is measured by Working Software + Evidence + Documentation, not activity volume.

## 53. OPERATIONAL EXECUTION CHECKLIST

### Pre-Execution
- Repository, branch, commit and working tree checked.
- Issue/PR and relevant workflows checked.
- Existing capability and duplicate work checked.
- Change class and execution path selected.
- Parallel opportunities and dependencies identified.
- Core/database/sync/security impact assessed.
- ADR, migration and rollback needs assessed.

### During Execution
- Scope and architecture boundaries maintained.
- Shared resources coordinated.
- No duplicate work.
- Fast analyze/test feedback used.
- New conflicts surfaced immediately.

### Post-Execution
- Code, commit and PR traceability established.
- Tests, CI and build evidence verified as applicable.
- Documentation and PROJECT_STATE updated.
- Review and conflict checks completed.
- Post-merge validation completed where applicable.

### Definition of Ready
Objective, Scope, Dependency, Owner, Validation and Integration Point are defined.

### Definition of Done
Working Software + Validation + Evidence + Documentation + Integration Safety.
