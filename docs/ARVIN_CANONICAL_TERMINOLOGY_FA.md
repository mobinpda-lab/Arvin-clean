# واژه‌نامه مرجع اصطلاحات آروین

- وضعیت: پیش‌نویس مرجع محصول؛ ممیزی سراسری رشته‌های UI هنوز کامل نشده است.
- تاریخ تهیه: 2026-10-13
- Issue پیگیری: #2669
- هدف: یکسان‌سازی زبان قابل مشاهده محصول بدون تغییر معنا، مدل داده یا رفتار.
- اصل حاکم: «یک مفهوم، یک نام اصلی در UI»؛ نام‌های فنی و مترادف‌های مجاز باید در همین سند ثبت شوند.

## 1. قواعد قطعی واژه‌گذاری

1. نام اصلی یک مفهوم در رابط کاربری باید در تمام صفحات، فرم‌ها، پیام‌ها، راهنماها، tooltipها و برچسب‌های دسترس‌پذیری یکسان باشد.
2. عنوان صفحه با نام عمومی قابلیت فرق دارد. عنوان عملیاتی باید با کاری که کاربر در همان لحظه انجام می‌دهد تطبیق کند.
3. شباهت واژه‌ها مجوز یکی‌کردن مفاهیم نیست؛ به‌ویژه «موعد»، «یادآور»، «پیگیری» و «اقدام بعدی» مستقل‌اند.
4. اصلاح متن به‌تنهایی نباید مدل، شناسه، Storage، تاریخچه یا داده را تغییر دهد. هیچ مهاجرت داده‌ای صرفاً برای اصلاح نام‌ها مجاز نیست.
5. اصطلاح انگلیسی داخلی مانند Task، Repository یا Projection ممکن است در کد باقی بماند؛ در UI باید از واژه فارسی روشن استفاده شود.
6. اگر دو نام در دو جای رابط دیده می‌شوند، ابتدا مشخص شود که آیا یکی نام قابلیت و دیگری عنوان عملیات است؛ قبل از تغییر باید رفتار و مسیرهای ورود بررسی شوند.
7. اسناد تاریخی برای حفظ سابقه حذف نشوند؛ در صورت تعارض باید به‌وضوح با برچسب تاریخی/منسوخ مشخص شوند.
8. این سند قرارداد واژه‌گذاری است، نه ادعای تأیید همه صفحات. وضعیت ممیزی هر رشته باید در «دفتر ممیزی» ثبت شود.

## 2. نام‌های عمومی و فرم‌های کار

| نام اصلی فارسی | اصطلاح انگلیسی/فنی | تعریف و کاربرد | نام‌های جایگزین/محدودیت |
|---|---|---|---|
| کار | Task | موجودیت اصلی کار و مرجع اطلاعات آن | «وظیفه» فقط اگر در متن توضیحی لازم باشد؛ نام اصلی UI «کار» |
| ثبت سریع کار | Quick Capture / Quick Add | مسیر کوتاه برای ثبت کار با حداقل اطلاعات | در متن UI از جابه‌جایی تصادفی بین «ثبت سریع»، «افزودن سریع» و «Quick Add» پرهیز شود |
| فرم کامل کار | Full Task Form / Full Editor | نام عمومی فرم دارای جزئیات کامل | برای نام قابلیت/مستندات مناسب است؛ لزوماً عنوان صفحه هنگام ویرایش نیست |
| افزودن کار | Create Task / Add Task | عنوان صفحه/عملیات هنگام ایجاد یک کار جدید | در فرم ایجاد استفاده شود |
| ویرایش کار | Edit Task | عنوان صفحه/عملیات هنگام تغییر یک کار موجود | عنوان مناسب هنگام ویرایش |
| جزئیات کار | Task Details | صفحه مشاهده اطلاعات کار و مسیرهای عملیاتی آن | با «ویرایش کار» یکی نیست |
| عنوان کار | Title | نام کوتاه کار | «عنوان» در صورت واضح بودن زمینه فرم مجاز است |
| توضیحات کار | Description | شرح اصلی کار | با یادداشت‌های پیگیری یا دفترچه یکی نیست |
| ذخیره | Save | نگهداری تغییرات فرم | «ثبت» می‌تواند برای ایجاد مورد جدید به‌کار رود؛ رفتار دکمه باید روشن باشد |
| لغو | Cancel | خروج بدون اعمال تغییرات فرم | در سراسر فرم‌ها یکسان |
| جزئیات بیشتر | More details | بازکردن بخش جزئیات تکمیلی در فرم | با صفحه «جزئیات کار» اشتباه نشود؛ اولی کنترل/بخش فرم است، دومی صفحه |

### قرارداد عنوان فرم
- قابلیت عمومی: «فرم کامل کار».
- ایجاد: «افزودن کار».
- ویرایش مورد موجود: «ویرایش کار».
- مشاهده: «جزئیات کار».
- «فرم کامل» و «ویرایش کار» را نباید بدون زمینه به‌عنوان دو قابلیت مستقل معرفی کرد. باید مسیر ورود، حالت create/edit و عنوان واقعی صفحه بررسی شود.

## 3. موعد، زمان و یادآورها

| نام اصلی فارسی | اصطلاح انگلیسی/شناسه | تعریف | مرز معنایی |
|---|---|---|---|
| موعد کار | Due Date / Task.dueDate | زمانی که انجام خود کار برای آن مقرر شده | به‌تنهایی اعلان نیست |
| موعد | Due | صورت کوتاه در فیلدهای کوچک، فقط وقتی زمینه کاملاً روشن است | در عنوان گزارش یا متن مستقل ترجیحاً «موعد کار» |
| یادآور | Reminder | سازوکار/موردی برای هشدار در زمان مشخص | با موعد کار یکی نیست |
| یادآور کار | Task Reminder | یادآور مستقل مرتبط با یک Task | چند یادآور می‌توانند به یک Task تعلق داشته باشند |
| زمان یادآور | Reminder Date/Time | تاریخ و ساعت هشدار | زمان موعد را تغییر نمی‌دهد |
| یادآور پیگیری | Follow-up Reminder | هشدار مرتبط با یک پیگیری | تاریخچه پیگیری یا اقدام بعدی نیست |
| تمام‌روز | All-day | رخداد دارای تاریخ بدون ساعت مشخص | نباید ساعت مصنوعی نیمه‌شب در UI یا ذخیره‌سازی القا شود |
| زمان شروع | Start Date/Time | آغاز برنامه یا بازه، اگر این مفهوم در آن قابلیت تعریف شده باشد | نباید با موعد یا یادآور جایگزین شود |
| زمان پایان | End Date/Time | پایان بازه، اگر تعریف شده باشد | باید معنای بازه حفظ شود |

قواعد:
- «موعد کار» مشخص می‌کند کار چه زمانی باید انجام شود.
- «یادآور» زمان هشدار را مشخص می‌کند.
- تغییر موعد نباید بی‌دلیل یادآور مستقل را تغییر دهد؛ هر وابستگی خودکار باید قرارداد جداگانه و صریح داشته باشد.
- در تقویم، نوع رویداد باید در برچسب روشن باشد؛ برای نمونه «موعد کار» با «یادآوری کار» یکی نشود.

## 4. پیگیری و اقدام بعدی

| نام اصلی فارسی | اصطلاح انگلیسی/شناسه | تعریف | مرز معنایی |
|---|---|---|---|
| پیگیری | Follow-up | اقدام/بررسی پیگیرانه مرتبط با موضوع یا کار | موجودیت/مفهومی مستقل از یادآور |
| پیگیری ثبت‌شده | Follow-up Entry | یک مورد ثبت‌شده در سابقه پیگیری | می‌تواند یادداشت، زمان یا جزئیات خود را داشته باشد |
| تاریخچه پیگیری | Follow-up History | فهرست سوابق پیگیری | تاریخچه را نباید با زمان اقدام آینده جایگزین کرد |
| آخرین پیگیری | Last Follow-up | جدیدترین مورد پیگیری ثبت‌شده | رویداد گذشته/ثبت‌شده است |
| پیگیری بعدی | nextFollowUp | زمان اقدام یا بررسی بعدی یک موضوع | با reminderDate یکی نیست |
| اقدام بعدی | Next Action | اقدام آینده‌ای که باید در اولویت قرار گیرد؛ همچنین نام یک نمای محصول | با نام یک سابقه پیگیری یکسان نیست |
| زمان پیگیری | Follow-up Schedule | زمان‌بندی مرتبط با پیگیری، مطابق زمینه قابلیت | در UI نوع زمان باید مشخص باشد |
| یادآور پیگیری | Follow-up Reminder | هشدار برای پیگیری | هشدار است، نه خود اقدام |
| کار پیگیری‌دار | Follow-up-enabled Task | کاری که قابلیت ثبت پیگیری برای آن فعال است | فعال‌بودن قابلیت لزوماً به معنی وجود یادآور نیست |

قواعد غیرقابل نقض:
- `nextFollowUp` و `reminderDate` دو مفهوم مستقل‌اند.
- «پیگیری بعدی» زمان اقدام/بررسی بعدی است؛ «یادآور» هشدار است.
- «اقدام بعدی» در نوار پایین نام یک مقصد/نما است؛ با یک فیلد تاریخ یا یک مورد تاریخچه یکی نیست.
- Follow-up Actionهای صرفاً نمایشی در تقویم نباید به‌طور ناخواسته اعلان بسازند یا وارد همگام‌سازی خروجی تقویم شوند.

## 5. تکرار، چک‌لیست و وضعیت

| نام اصلی فارسی | اصطلاح انگلیسی/فنی | تعریف | محدودیت |
|---|---|---|---|
| تکرار | Repeat / Recurrence | برنامه تکرار کار | نباید با ساخت نسخه‌های مستقل و تکراری Task اشتباه شود |
| الگوی تکرار | Recurrence Rule | قانون تعریف نوبت‌های تکرار | جزئیات فنی فقط در UI پیشرفته لازم است |
| تناوب تکرار | Recurrence Frequency | فاصله زمانی نوبت‌ها | با تاریخ شروع/پایان تکرار فرق دارد |
| تکرار سفارشی | Custom Recurrence | تنظیم تناوب دلخواه | در ثبت سریع و فرم کامل باید معنای سازگار داشته باشد |
| نوبت تکرار | Occurrence | یک نوبت از برنامه کار تکرارشونده | نوبت‌های گذشته نباید با ویرایش آینده بازنویسی شوند |
| ادامه از امروز | Resume From Today | بازتنظیم برنامه آینده از امروز | تاریخچه و انجام‌های قبلی را تخریب نمی‌کند |
| چک‌لیست | Checklist | فهرست مواردی که برای تکمیل همان کار انجام می‌شوند | بخشی از Task است، نه موجودیت ذخیره‌سازی موازی |
| مورد چک‌لیست | Checklist Item | یک ردیف در چک‌لیست | وضعیت هر مورد باید مستقل قابل تغییر باشد |
| پیشرفت چک‌لیست | Checklist Progress | میزان انجام موارد چک‌لیست | با وضعیت نهایی Task یکی نیست |
| اهمیت | Priority | درجه اهمیت کار | با وضعیت انجام فرق دارد |
| وضعیت | Status | وضعیت چرخه عمر کار | با اولویت یکی نیست |
| انجام‌شده | Completed | کار/نوبت تکمیل شده است | نباید صرفاً از روی موعد استنتاج شود |
| بایگانی‌شده | Archived | کار از فهرست فعال کنار گذاشته شده | با حذف دائمی یکی نیست |
| سطل زباله | Trash | محل نگهداری موارد حذف‌شده قابل بازیابی، طبق رفتار محصول | با بایگانی یکی نیست |

| نام اصلی فارسی | اصطلاح انگلیسی | تعریف | قرارداد |

## 8. اصطلاحات فنی داخلی؛ نه برای متن معمول UI

| اصطلاح | معنی ساده | کاربرد مناسب |
|---|---|---|
| Canonical Task | کار مرجع و اصلی | اسناد معماری/کد |
| Source of Truth | منبع نهایی و معتبر داده | معماری |
| Model | ساختار داده | کد و مستندات فنی |
| Repository | لایه دسترسی به داده | کد و مستندات فنی |
| Persistence | ذخیره‌سازی پایدار | مستندات فنی |
| Migration | انتقال/تبدیل نسخه‌دار داده | مستندات فنی |
| Serialization | تبدیل داده به قالب ذخیره/انتقال | مستندات فنی |
| Projection | نمایش داده مرجع در مقصد دیگر | معماری تقویم/گزارش |
| Stable ID | شناسه پایدار | معماری و عیب‌یابی |
| Backup/Restore round-trip | بررسی ذخیره و بازیابی کامل | آزمون فنی |
| RTL | راست‌به‌چپ | طراحی/کد |
| UI | رابط کاربری | مستندات فنی |
| CI | بررسی و آزمون خودکار | گزارش فنی |
| Release | نسخه آماده انتشار | مدیریت انتشار |

در UI به‌جای «Projection»، عبارتی مانند «رویداد تقویم» یا «نمایش در تقویم» استفاده شود؛ به‌جای «Persistence»، «ذخیره اطلاعات»؛ و به‌جای «Restore»، «بازیابی نسخه پشتیبان».

## 9. دفتر ممیزی اولیه: موارد دیده‌شده و اقدام لازم

| مورد | شواهد اولیه | طبقه‌بندی فعلی | اقدام لازم |

| «یادآور» / «یادآوری» / «یادآوری کار» | Quick Capture، Task Editor و Work Agenda | صورت‌های وابسته به بافت | «یادآور» برای فیلد/مورد؛ «یادآوری کار» برای نوع رویداد؛ متن‌های باقی‌مانده بررسی شوند |
| «دسته» / «گروه» | سند مرجع UI و Issue #2580 | قرارداد قطعی موجود | حفظ «دسته» در UI دامنه‌ای؛ بررسی همه منوها، فرم‌ها، راهنما و اسناد |
| «پیگیری» / «اقدام بعدی» | نوار اصلی، صفحه اقدام بعدی و فرم ثبت سریع | دو مفهوم مرتبط اما مستقل | حفظ تفکیک معنایی؛ جست‌وجوی مواردی که یکی به جای دیگری استفاده شده |
| «توضیحات» / «یادداشت» | فرم کار، پیگیری و دفترچه | احتمال تداخل معنایی | بافت هر فیلد و مالک داده بررسی شود؛ ادغام داده ممنوع |

| «تقویم» / «تقویم دستگاه» | مقصد داخلی آروین و تقویم خارجی | دو مقصد متفاوت | هنگام عملیات خارجی، «تقویم دستگاه» یا نام تقویم مقصد روشن باشد |

این دفتر فهرست اولیه موارد کشف‌شده است؛ به معنی استخراج کامل تمام رشته‌های پروژه نیست.

## 10. طبقه‌بندی هر نتیجه در ممیزی سراسری

هر رشته/شناسه باید دقیقاً در یکی از گروه‌های زیر ثبت شود:

- **A — نام اصلی:** مطابق واژه‌نامه و مناسب UI.
- **B — مترادف مجاز:** تنها در بافت مشخص و با دلیل روشن مجاز است.
- **C — اصطلاح فنی داخلی:** در کد/سند فنی مجاز، در UI معمولاً ممنوع.
- **D — تاریخی/منسوخ:** برای حفظ سابقه باقی می‌ماند اما نباید قرارداد فعلی تلقی شود.
- **E — ناسازگاری نیازمند اصلاح:** یک مفهوم با نام‌های متعارض یا واژه‌ای که مفهوم نادرست القا می‌کند.
- **F — نیازمند تصمیم محصول:** شواهد برای تصمیم قطعی کافی نیست؛ تا تصمیم، تغییر معنایی انجام نشود.
