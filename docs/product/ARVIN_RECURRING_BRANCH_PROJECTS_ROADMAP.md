## 1. هدف محصول
کاربر فهرست شعب و مراکز را یک‌بار ثبت می‌کند، فرایندهای تکراری را در قالب پروژه طراحی می‌کند و در هر دوره، از یک قالب برای یک یا چند شعبه پروژه‌های اجرایی مستقل می‌سازد؛ بدون ورود مجدد اطلاعات. خروجی باید بر اساس شعبه، قالب، دوره و وضعیت قابل گزارش‌گیری باشد.
اصل حاکم: **Branch = محل اجرا؛ Template = الگوی فرایند؛ Project = اجرای واقعی؛ Task = اقدام اجرایی؛ Tag = برچسب جانبی.** این مفاهیم جایگزین یکدیگر نیستند.
## 2. سلسله‌مراتب و روابط داده — تصمیم قطعی محصول
1. **Branch → Projects: یک‌به‌چند (One-to-Many).** هر شعبه/مرکز می‌تواند در طول زمان و هم‌زمان میزبان چند Project مستقل باشد.
2. **Project → Tasks: یک‌به‌چند (One-to-Many).** هر Project شامل Taskهای اجرایی مستقل است. هنگام تولید از Template، Taskهای نمونه به Project جدید کپی می‌شوند.
3. **Historical Segregation — جداسازی تاریخی.** Projectهای دوره‌های مختلف یک Branch رکوردهای مستقل‌اند؛ ایجاد یا ویرایش اجرای جدید نباید Projectهای قبلی را بازنویسی کند. تاریخچه هر Branch باید قابل بازیابی و گزارش‌گیری باقی بماند.
4. **Template → Project: رابطه منشأ/ردیابی، نه مالکیت اجرایی.** هر Project تولیدشده می‌تواند Template مبدأ را برای گزارش و ردیابی نگه دارد؛ تغییر Template نباید به Projectهای ساخته‌شده سرایت کند.
5. **اختیاری‌بودن اتصال‌ها.** Projectهای موجود و آینده که از این قابلیت استفاده نمی‌کنند، همچنان می‌توانند بدون Branch و بدون Template معتبر باشند. تعیین Branch برای همه Projectها اجباری نمی‌شود.
6. **عدم مدل موازی.** Project و Task فعلی منبع اصلی رفتار و ذخیره‌سازی باقی می‌مانند. Branch و Project Template مفاهیم جدید ساختاری‌اند، اما نباید مدل موازی برای Task یا Project اجرایی بسازند.
## 3. تعاریف موجودیت‌ها
### 3.1 Branch / Center — شعبه یا مرکز
پاسخ «پروژه برای کجا انجام می‌شود؟»؛ مرجع مستقل و ساختاریافته، نه Tag.
حداقل فیلدهای محصولی نسخه اول:
- شناسه پایدار؛
- نام؛
- کد اختیاری؛
- توضیح اختیاری؛
- وضعیت فعال/غیرفعال.
شعبه دارای سابقه Project حذف مخرب نمی‌شود؛ فقط غیرفعال می‌شود. تغییر نام یا وضعیت Branch نباید شناسه و تاریخچه Projectهای آن را از بین ببرد.
### 3.2 Project Template — قالب پروژه
پاسخ «این فرایند معمولاً چگونه انجام می‌شود؟»؛ تعریف قابل استفاده مجدد از فرایند، نه اجرای واقعی.
شامل عنوان، توضیحات و مجموعه Taskهای نمونه است. به Branch یا تاریخ مشخص وابسته نیست، در فهرست Projectهای فعال نمایش داده نمی‌شود و می‌تواند مشاهده، ایجاد، ویرایش، کپی و غیرفعال شود.
فرمان «ذخیره به‌عنوان قالب» از Project موجود یک Template مستقل می‌سازد؛ Project اصلی باقی می‌ماند و ماهیت یا شناسه آن تغییر نمی‌کند.
### 3.3 Project — پروژه اجرایی
اجرای واقعی یک فرایند برای یک Branch و یک دوره مشخص است. می‌تواند Branch و Template مبدأ داشته باشد یا هر دو را نداشته باشد.
عنوان پیشنهادی از ترکیب عنوان Template و نام Branch ساخته می‌شود و کاربر می‌تواند آن را ویرایش کند. دوره، تاریخ شروع و مهلت در صورت نیاز ثبت می‌شوند.
### 3.4 Task — کار اجرایی
اقدام مستقل داخل Project است. در زمان تولید Project از Template، Taskهای نمونه کپی می‌شوند؛ پس از ایجاد، Taskهای Project از Template و Projectهای دیگر مستقل‌اند. تکمیل، حذف یا ویرایش Task در یک اجرا نباید نمونه Template یا Taskهای اجرای دیگر را تغییر دهد.
### 3.5 Tag — برچسب
ویژگی جانبی یا موقت Project یا Task مانند «فوری»، «نیازمند قطعه»، «نیازمند تأیید» یا «بازرسی ویژه». Tag هویت Branch، Template یا دوره را مدل نمی‌کند و جایگزین روابط ساختاری نیست.
## 4. جریان‌های اصلی کاربر
### 4.1 دفترچه شعب
- ایجاد، مشاهده، ویرایش و غیرفعال‌کردن Branch؛
- نمایش تاریخچه Projectهای همان Branch؛
- حفظ تاریخچه با تغییر نام؛
- جلوگیری از حذف مخرب Branch دارای سابقه.
### 4.2 کتابخانه قالب‌ها
- ساخت Template مستقل؛
- ذخیره Project موجود به‌عنوان Template بدون حذف یا تبدیل Project اصلی؛
- مشاهده، ویرایش، کپی و غیرفعال‌کردن Template؛
- اعمال تغییر Template فقط بر اجراهای آینده، نه Projectهای قبلی.
### 4.3 تولید Project از Template
1. انتخاب Template؛
2. انتخاب یک یا چند Branch فعال؛
3. تعیین اختیاری عنوان دوره، تاریخ شروع و مهلت؛
4. پیش‌نمایش تعداد Projectهای قابل ایجاد و نام پیشنهادی هرکدام؛
5. بررسی هشدارهای تکرار؛
6. تأیید آگاهانه کاربر؛
7. ایجاد یک Project مستقل برای هر Branch انتخاب‌شده و کپی Taskهای Template در همان Project.
برای N شعبه انتخاب‌شده، خروجی مورد انتظار N Project مستقل است؛ در مثال پنج Branch، دقیقاً پنج Project مستقل با Taskهای مستقل ساخته می‌شود.
هر Project باید Branch و Template مبدأ را در جزئیات خود به‌صورت قابل مشاهده نشان دهد.

## 5. گزارش‌گیری و فیلترها
1. **Branch:** همه Projectهای جاری و تاریخی یک شعبه؛
2. **Template:** همه اجراهای ساخته‌شده از یک Template در شعب مختلف؛
3. **Period:** Projectهای متعلق به یک نوبت/بازه مشخص؛
4. **Status:** شروع‌نشده، در حال انجام، تکمیل‌شده، عقب‌افتاده؛
5. **Tag:** فیلتر مکمل برای برچسب‌هایی مانند نیازمند قطعه یا تأیید.
6. **Task-specific Follow-ups:** نمایش و فیلتر تمام رکوردهای پیگیری متصل به یک Task مشخص، با حفظ شناسه همان Task و بدون مخلوط‌کردن پیگیری‌های کارهای دیگر.
7. **Combined filters:** ترکیب هم‌زمان چند معیار (برای نمونه Branch + Template + Period + Status + Tag و در صورت انتخاب، Task/Follow-up)؛ نتیجه باید حاصل اشتراک معیارهای انتخاب‌شده باشد و حذف/تغییر یک معیار، سایر معیارها را ناخواسته پاک نکند.
8. **Point filters:** پشتیبانی از فیلترهای نقطه‌ای طبق درخواست مالک محصول. تعریف دقیق واحد انتخاب، دامنه و رفتار این فیلترها پیش از طراحی UX/Query باید با مالک محصول تثبیت شود؛ تا آن زمان هیچ معنای فنی یا رابطی حدس زده نمی‌شود.
فیلترها فقط زمانی در محصول فعال معرفی می‌شوند که Query و داده واقعی از آن‌ها پشتیبانی کنند. معنای دقیق «عقب‌افتاده» باید با قواعد وضعیت فعلی Project/Task هم‌راستا شود و از مقدار ساختگی مشتق نشود.

### 5.1 مرکز یکپارچه گزارش‌ها — Reports Tab
- تمام گزارش‌های مرتبط با Branch/Center، Template و Period فقط در بخش واحد «گزارش‌ها» (Reports Tab) سازمان‌دهی و ارائه می‌شوند؛ این گزارش‌ها به صفحات یا تب‌های پراکنده و موازی منتقل نمی‌شوند.
- در Reports Tab فیلتر اختصاصی Branch/Center برای محدودکردن Projectها و Taskهای همان شعبه/مرکز وجود دارد؛ انتخاب یک Branch باید گزارش جاری و تاریخی همان Branch را بر اساس داده واقعی نشان دهد.
- گزارش‌های Template و Period در همان مرکز ارائه می‌شوند و امکان ترکیب آن‌ها با Branch، Status، Tag و معیارهای معتبر دیگر وجود دارد.
- گزارش پیگیری‌ها از رکوردهای واقعی Follow-up و رابطه آن‌ها با Task استخراج می‌شود؛ انتخاب یک Task فقط پیگیری‌های همان Task را نشان می‌دهد.
- گزارش‌ها باید حالت‌های بدون نتیجه، خطا، بارگذاری و تعداد نتایج را شفاف نشان دهند؛ نبود داده نباید با مقدار یا رکورد ساختگی پر شود.
- Reports Tab محل تجمیع و مشاهده گزارش است؛ ایجاد این بخش نباید منبع ذخیره‌سازی یا مدل موازی برای Project، Task یا Follow-up بسازد.
## 6. جلوگیری از تولید تکراری و شکست گروهی
- پیش از تولید گروهی، تعداد و فهرست Projectهای قابل ایجاد نمایش داده شود.
- ترکیب Template + Branch + Period برای تشخیص تکرار بررسی شود.
- اگر برای همین ترکیب Project فعال یا ثبت‌شده وجود دارد، هشدار روشن با امکان مشاهده مورد قبلی نمایش داده شود.
- تکرار فقط پس از تأیید صریح و آگاهانه کاربر مجاز است.
- هویت/نرمال‌سازی Period و سیاست دقیق تشخیص «تکرار» باید پیش از طراحی پایگاه داده تثبیت شود؛ این سند فعلاً قید محصولی را ثبت می‌کند و Constraint دیتابیسی را تجویز نمی‌کند.
- نتیجه تولید برای هر Branch مشخص باشد: ایجادشده، ردشده به‌علت تکرار، یا ناموفق همراه علت. شکست جزئی نباید به‌صورت موفقیت کامل یا نتیجه مبهم گزارش شود.
- پیش از اجرا باید سیاست تراکنش گروهی (همه یا هیچ در برابر نتیجه مستقل هر Branch) در طراحی فنی تعیین و در UI به‌وضوح بازتاب داده شود؛ رفتار ضمنی یا پنهان پذیرفته نیست.

- Project و Task فعلی، مسیر اصلی و منبع حقیقت باقی می‌مانند.
- Projectهای قدیمی بدون Branch و Template بدون تغییر و بدون الزام به مهاجرت اجباری قابل استفاده می‌مانند.

- تغییر یا غیرفعال‌سازی Branch نباید تاریخچه Projectها را حذف یا بازنویسی کند.
- مهاجرت احتمالی باید غیرمخرب، قابل تکرار، قابل بازیابی و مبتنی بر Backup معتبر باشد؛ هیچ Project، Task، Reminder، Snooze، Completion، تاریخچه یا File Persistence نباید از دست برود.
- Branch با Tag جایگزین نمی‌شود و Tag نباید هویت ساختاری را حمل کند.
- هیچ قابلیت منسوخ Next Follow-up یا متغیر ساختگی `followUpEnabled` برای مدل‌سازی دوره، وضعیت یا اقدام بعدی بازگردانده نمی‌شود. زمان‌بندی‌های آینده موجود در قرارداد Reminder مستقل باقی می‌مانند.
## 10. معیارهای پذیرش محصول
1. کاربر هر Branch را یک‌بار ثبت کند و بتواند بعداً آن را ویرایش یا غیرفعال کند.
2. کاربر هر فرایند را یک‌بار به‌صورت Template طراحی کند.
3. انتخاب پنج Branch، دقیقاً پنج Project اجرایی مستقل تولید کند.
4. هر Project تمام Taskهای Template را به‌صورت نسخه‌های مستقل داشته باشد.
5. تکمیل/ویرایش Task در یک Project، Projectهای دیگر یا Template را تغییر ندهد.
6. ویرایش Template، Projectهای قبلی را تغییر ندهد.
7. تاریخچه Branch مستقل، کامل و قابل گزارش‌گیری باشد.
8. Projectهای قدیمی بدون Branch/Template همچنان کار کنند.
9. Branch یک موجودیت ساختاری مستقل باشد و با Tag جایگزین نشود.
10. ایجاد تکراری ناخواسته پیش از تأیید کاربر متوقف و هشدار داده شود.
11. شکست گروهی برای هر Branch با نتیجه و علت روشن گزارش شود.
12. هیچ داده، تست یا رفتار تثبیت‌شده فعلی آسیب نبیند.
13. هیچ ارجاع شکسته، `#REF`، رکورد یتیم یا رابطه نامعتبر پس از عملیات/مهاجرت باقی نماند.
14. غیرفعال‌سازی Branch یا Template تاریخچه Projectهای موجود را مخدوش نکند.
15. تولید و گزارش‌گیری بر اساس Branch، Template، Period، Status و Tag با داده واقعی انجام شود.

## 14. الزام چیدمان جست‌وجوی سراسری صفحه اصلی — Home UI

- متن راهنمای ورودی (placeholder): «جستجو در کارها، پروژه‌ها و شعب»؛ جست‌وجو باید واقعی و متصل به داده‌های موجود باشد، نه صرفاً تزئینی.
- دامنه جست‌وجوی سراسری شامل **کارها (Tasks)، پروژه‌ها (Projects) و شعب/مراکز (Branches/Centers)** است. نتایج باید نوع موجودیت را روشن نشان دهند و انتخاب نتیجه شعبه باید امکان ورود مستقیم به جزئیات/فهرست پروژه‌ها و تاریخچه همان شعبه را فراهم کند.

- کارت شعبه/مرکز باید به دفترچه شعب (Branch Directory) متصل باشد و فهرست شعب فعال را برای دسترسی سریع ارائه کند؛ تاریخچه شعب غیرفعال از مسیر گزارش‌ها/جزئیات قابل دسترسی باقی می‌ماند و با غیرفعال‌سازی حذف نمی‌شود.
- این الزام، توسعه جایگاه جست‌وجو و افزودن کارت پنجم است و به‌تنهایی مجوز بازطراحی کلی Home یا تغییر رفتار سایر کارت‌ها نیست.
- مالک محصول به تصویر مرجع اشاره کرده است، اما فایل/شناسه تصویر در شواهد قابل بازیابی این ثبت حاضر نیست؛ بنابراین ساختار پنج‌کارتی، دامنه جست‌وجو و جایگاه آن ثبت شده، ولی تطبیق پیکسل‌به‌پیکسل رنگ، اندازه، شعاع، فاصله و جزئیات ظاهری تصویر مرجع فعلاً `NOT VERIFIED` است و پیش از پیاده‌سازی بصری باید با همان تصویر تأیید شود.

## 15. تصمیم‌های UX/گزارش که پیش از پیاده‌سازی باید تثبیت شوند
1. تعریف دقیق «فیلتر نقطه‌ای»: واحد داده/زمان/رویداد قابل انتخاب، حالت تک‌نقطه‌ای یا چندنقطه‌ای، و نحوه ترکیب آن با سایر فیلترها.
2. فهرست فیلدهای قابل فیلتر در رکورد Follow-up یک Task (مانند تاریخ/بازه، وضعیت یا نتیجه، شخص و متن) فقط بر اساس فیلدهای واقعاً موجود و معتبر تعیین شود؛ هیچ فیلد تازه یا وضعیت ساختگی مفروض نیست.
3. رفتار AND/OR برای گروه‌های مختلف فیلتر و امکان ذخیره/پاک‌کردن ترکیب‌ها در طراحی UX مشخص شود؛ پیش‌فرض ترکیب معیارهای انتخاب‌شده اشتراک (AND) است مگر مالک محصول تصمیم دیگری بگیرد.
4. تصویر مرجع Home و معیارهای ظاهری دقیق آن باید به سند/مخزن متصل شود تا تطبیق بصری قابل ممیزی باشد.


## 16. تصمیم نهایی مالک محصول — پنج دسترسی سریع و جست‌وجوی Branch-aware در Home
- تعداد کارت‌های دسترسی سریع صفحه اصلی دقیقاً پنج مورد است: برچسب‌ها، دسته‌ها، پروژه‌ها، زمان و شعبه/مرکز.
- جست‌وجوی سراسری Home باید کارها، پروژه‌ها و شعب/مراکز را پشتیبانی کند و امکان فیلتر مستقیم بر اساس Branch/Center داشته باشد.
- این تصمیم، بندهای چهارکارتی و جست‌وجوی صرفاً Task-based در نسخه قبلی همین سند را جایگزین می‌کند؛ معیار جدید مرجع است.
- نتیجه جست‌وجو باید نوع موجودیت را مشخص کند و فیلتر Branch بر رابطه ساختاری واقعی تکیه کند؛ از جست‌وجوی متنیِ صرف به‌عنوان معادل فیلتر شعبه استفاده نشود.
- این تغییر فقط مشخصات محصول است. پیاده‌سازی Home، تغییر کد اجرایی، تغییر Schema/Migration یا تغییر رفتار برنامه تا پذیرش تست‌های پایداری و صدور مجوز اجرایی مستقل ممنوع است.


## 17. فهرست نهایی و قفل‌شدهٔ پنج تغییر محصول‌محور — تصمیم مالک محصول 2026-11-02

این فهرست، مرجع واحد و نهایی دامنه محصولی این گفتگو است. پنج بسته زیر به‌عنوان نیازمندی رسمی ثبت می‌شوند؛ وضعیت همه آن‌ها POST-STABILITY / PLANNED است، نه پیاده‌سازی‌شده و نه پذیرفته‌شده:

1. **ساختار شعب، پروژه‌ها و تاریخچه:** Branch/Center موجودیت ساختاری مستقل است؛ رابطه Branch → Projects یک‌به‌چند و Project → Tasks یک‌به‌چند است. Projectهای هر شعبه و هر دوره مستقل و تاریخی باقی می‌مانند؛ Projectهای قدیمی بدون Branch معتبرند؛ شعبه دارای سابقه حذف مخرب نمی‌شود و فقط غیرفعال می‌شود.
2. **کتابخانه قالب‌ها و تولید پروژه‌های تکرارشونده:** Template Library، ذخیره Project موجود به‌عنوان Template، انتخاب یک یا چند Branch فعال و تولید یک Project مستقل برای هر Branch با کپی مستقل Taskها. تغییر Template نباید به Projectهای تولیدشده قبلی سرایت کند؛ کنترل تکرار و نتیجه هر Branch باید شفاف باشد.
3. **مرکز متمرکز گزارش‌ها و فیلترهای پیشرفته:** همه گزارش‌های Branch/Center، Template و Period در یک Reports Tab قرار می‌گیرند. فیلتر اختصاصی شعبه، Status و Tag، گزارش Follow-up محدود به Task منتخب، ترکیب معیارها و Point filters در دامنه محصول هستند. معنای دقیق Point filters و برخی قواعد UX/Query همچنان نیازمند تصمیم طراحی صریح‌اند و نباید حدس زده شوند.
4. **صفحه اصلی پنج‌بخشی:** دقیقاً پنج کارت دسترسی سریع هم‌اندازه و آیکون‌دار: برچسب‌ها، دسته‌ها، پروژه‌ها، زمان و شعبه/مرکز؛ ترتیب RTL از راست به چپ: زمان، پروژه‌ها، دسته‌ها، برچسب‌ها، شعبه/مرکز. کارت شعبه به Branch Directory متصل است.
5. **جست‌وجوی سراسری پیشرفته و آگاه از شعبه:** جست‌وجوی Home روی داده واقعی Tasks، Projects و Branches/Centers کار می‌کند؛ نوع موجودیت در نتیجه مشخص است؛ فیلتر مستقیم شعبه باید بر شناسه و رابطه ساختاری Branch متکی باشد، نه صرفاً تطبیق متن نام شعبه. نتیجه شعبه باید مسیر دسترسی به جزئیات، پروژه‌ها و تاریخچه همان شعبه را فراهم کند.

**قفل دامنه:** این پنج مورد جایگزین هر برداشت قدیمی ناسازگار (از جمله Home چهارکارتی یا جست‌وجوی صرفاً Task-based) هستند. تغییر، حذف یا گسترش این دامنه فقط با دستور صریح بعدی مالک محصول مجاز است. این قفل، جزئیات طراحی حل‌نشده را به تصمیم فنی تبدیل نمی‌کند.

**مرز اجرا:** تا اتمام تست‌های پایداری و صدور دستور اجرایی مستقل، هیچ کد اجرایی، تغییر UI/runtime، Schema، Migration، مدل یا ذخیره‌سازی جدید برای این پنج بسته مجاز نیست. کار فنی جاری فقط باید شواهد پایداری SQLite را ببندد. هیچ تست یا Assertion موجود نباید حذف، Skip، تضعیف یا با Timeout صوری سبز شود.

## 18. تصمیم راهبردی مالک محصول — SSOT مرکزی و یکپارچگی داده بین بخش‌ها — 2026-11-02

**اصل الزام‌آور SSOT:** تمام دسته‌ها (Category)، برچسب‌ها (Tag)، پروژه‌ها (Project) و شعب/مراکز (Branch/Center) باید منحصراً از یک هسته مرکزی مدیریت داده در بخش تنظیمات تغذیه شوند. Settings Management Hub نقطه واحد مدیریت این موجودیت‌ها است؛ سایر بخش‌ها فقط مصرف‌کننده داده canonical هستند و حق ساخت کاتالوگ، مدل یا ذخیره‌سازی موازی ندارند.

**انتشار تغییر:** هر ایجاد، ویرایش، تغییر نام، غیرفعال‌سازی یا حذف مجاز باید از مسیر نوشتن canonical واحد عبور کند. پس از موفقیت پایدار، تغییر باید در فرم ثبت سریع، فرم کامل ثبت/ویرایش، پنج دسترسی سریع Home، جست‌وجوی سراسری، فیلترها، Reports و Calendar منعکس شود. Snapshotهای UI صرفاً موقت‌اند و باید پس از mutation یا بازگشت از Settings تازه‌سازی/invalidate شوند؛ نگهداری فهرست مستقل و قدیمی پذیرفته نیست.

**حفاظت سازگاری:** تغییرات چندبخشی شامل کاتالوگ و ارجاع‌های Task باید اتمیک باشند. شکست ذخیره نباید اجازه دهد فقط بخشی از Category/Tag/Project/Branch تغییر کند. هویت و رابطه ساختاری Branch باید مبنای فیلتر و جستجو باشد؛ تطبیق متنی نام شعبه کافی نیست. حذف Branch دارای سابقه مخرب نیست و Projectهای قدیمی بدون Branch معتبر باقی می‌مانند.

**وضعیت در HEAD ممیزی‌شده:** الزام محصولی ثبت شده، اما SSOT سراسری پیاده‌سازی یا پذیرفته نشده است. ممیزی کد نشان می‌دهد Category هم در taxonomy_categories و هم در tasks.category ذخیره می‌شود؛ rename کاتالوگ و ارجاع Task در دو عملیات جدا انجام می‌شود؛ Tag در tags/task_tags و Project در projects/project_items نگهداری می‌شوند؛ Branch model/table/store در مسیرهای بررسی‌شده مشاهده نشد. ## 19. تصمیم تکمیلی مالک محصول — نمایش سلسله‌مراتب، کارت کار و فیلترهای اصلی — 2026-11-02

این بند تکمیل‌کننده تصمیم‌های قبلی مالک محصول است و آن‌ها را لغو یا کوچک نمی‌کند. تصمیم مبین برای پیاده‌سازی این قابلیت‌ها پابرجاست. ثبت این مشخصات به معنی پایان توسعه، پذیرش محصول یا مجوز تغییر main نیست.

### 19.1 رابطه ساختاری و حفظ سوابق
- رابطه قابل مشاهده و قابل پیمایش محصول باید **شعبه/مرکز ← پروژه ← کارها** باشد؛ هر پروژه زیر شعبه/مرکز مربوط و هر کار زیر پروژه مربوط نمایش داده شود.
- این نمایش باید از رابطه و شناسه‌های واقعی داده پیروی کند، نه از Tag، متن نام یا گروه‌بندی نمایشی.
- سوابق پروژه‌ها و کارهای دوره‌های قبلی باید حفظ و قابل بازیابی بمانند؛ تغییر نام یا غیرفعال‌سازی شعبه نباید تاریخچه را حذف یا به پروژه/شعبه دیگری منتقل کند.
- پروژه‌های قدیمیِ بدون شعبه معتبر همچنان معتبرند و نباید برای نمایش سلسله‌مراتب به‌زور به شعبه‌ای متصل شوند.
- **باز و بسته شدن خودِ گره شعبه یا پروژه** در درخت/فهرست، الزام محصولی مصوب این بند نیست؛ تا تصمیم مستقل مبین، رفتار expand/collapse برای این دو گره نباید به‌عنوان الزام قطعی معرفی یا پیاده‌سازی شود.

### 19.2 کارت «کار» در صفحه اصلی
- کارت هر کار در Home باید امکان باز و بسته شدن داشته باشد تا کاربر بدون ترک فهرست، توضیحات و زمان دقیق همان کار را مشاهده کند.
- در حالت باز، توضیحات و تاریخ/ساعت دقیق ثبت‌شده برای همان Task نمایش داده شود؛ مقدار زمان نباید از داده دیگری حدس زده شود.
- مسیر مستقل صفحه جزئیات کار باید حفظ شود و باز/بسته‌کردن کارت جایگزین یا حذف مسیر جزئیات نیست.
- وضعیت کد در HEAD ثبت‌شده: قابلیت بازشدن کارت، نمایش توضیح و زمان دقیق و حفظ اقدام مستقل Task Details در سابقه CHANGELOG پیاده‌سازی شده است؛ پذیرش نهایی آن همچنان منوط به تست‌های معتبر روی SHA نهایی و شاهد UI/دستگاه است.

### 19.3 آخرین پیگیری معتبر همان کار
- کارت کار باید آخرین رکورد معتبر Follow-up متعلق به **همان Task** را از سرویس واقعی نمایش پیگیری دریافت و نمایش دهد.
- منبع نمایش باید داده persisted و رابطه واقعی Follow-up ↔ Task باشد؛ پیگیری کار دیگر، تاریخ legacy یا مقدار نمایشی/ساختگی نباید به‌عنوان آخرین پیگیری نشان داده شود.
- پیاده‌سازی ثبت‌شده در CHANGELOG از HomeFollowUpPresentationService و task.lastFollowUp استفاده می‌کند؛ این سابقه، شاهد وجود تغییر کد است و به‌تنهایی پذیرش نهایی رفتار را اثبات نمی‌کند.
- بازگرداندن قابلیت منسوخ **Next Follow-up** یا متغیر ساختگی followUpEnabled ممنوع است. این سند مجوز افزودن دوباره فیلد، ستون، مدل یا زمان‌بندی موازی نیست.

### 19.4 نوار فیلتر فهرست کارها
- نوار فیلتر اصلی باید گزینه **«همه»** و پنج فیلتر تخصصی مستقل داشته باشد: **زمان، پروژه‌ها، شعبه/مرکز، دسته‌بندی‌ها و برچسب‌ها**.
- «همه» حالت بدون محدودسازی این پنج معیار است. انتخاب هر فیلتر باید به داده و رابطه canonical متصل باشد و نتیجه واقعی را محدود کند؛ برچسب یا فیلتر نمایشی بدون Query واقعی پذیرفته نیست.
- فیلتر شعبه/مرکز باید بر شناسه و رابطه ساختاری Branch → Project → Task تکیه کند، نه تطبیق متنی نام شعبه.
- رفتار ترکیب فیلترها، پاک‌کردن انتخاب‌ها، حالت بدون نتیجه و تازه‌سازی پس از تغییر داده باید در طراحی و تست مشخص باشد. تا زمانی که تصمیم دقیق AND/OR یا رفتار ترکیب به‌صورت جداگانه تثبیت نشده، هیچ رفتار متناقضی نباید حدس زده شود.

### 19.5 وضعیت و مرز اجرا
- تصمیم مالک محصول برای پیاده‌سازی این قابلیت‌ها حفظ و ثبت می‌شود؛ آن‌ها از دامنه محصول حذف نشده‌اند.
