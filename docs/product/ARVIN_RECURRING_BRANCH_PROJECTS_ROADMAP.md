## 1. هدف محصول
کاربر فهرست شعب و مراکز را یک‌بار ثبت می‌کند، فرایندهای تکراری را در قالب پروژه طراحی می‌کند و در هر دوره، از یک قالب برای یک یا چند شعبه پروژه‌های اجرایی مستقل می‌سازد؛ بدون ورود مجدد اطلاعات. خروجی باید بر اساس شعبه، قالب، دوره و وضعیت قابل گزارش‌گیری باشد.
اصل حاکم: **Branch = محل اجرا؛ Template = الگوی فرایند؛ Project = اجرای واقعی؛ Task = اقدام اجرایی؛ Tag = برچسب جانبی.** این مفاهیم جایگزین یکدیگر نیستند.
## 2. سلسله‌مراتب و روابط داده — تصمیم قطعی محصول
1. **Branch → Projects: یک‌به‌چند (One-to-Many).** هر شعبه/مرکز می‌تواند در طول زمان و هم‌زمان میزبان چند Project مستقل باشد.
2. **Project → Tasks: یک‌به‌چند (One-to-Many).** هر Project شامل Taskهای اجرایی مستقل است. هنگام تولید از Template، Taskهای نمونه به Project جدید کپی می‌شوند.
3. **Historical Segregation — جداسازی تاریخی.** Projectهای دوره‌های مختلف یک Branch رکوردهای مستقل‌اند؛ ایجاد یا ویرایش اجرای جدید نباید Projectهای قبلی را بازنویسی کند. تاریخچه هر Branch باید قابل بازیابی و گزارش‌گیری باقی بماند.
4. **Template → Project: رابطه منشأ/ردیابی، نه مالکیت اجرایی.** هر Project تولیدشده می‌تواند Template مبدأ را برای گزارش و ردیابی نگه دارد؛ تغییر Template نباید به Projectهای ساخته‌شده سرایت کند.
5. **اختیاری‌بودن اتصال‌ها.** Projectهای موجود و آینده که از این قابلیت استفاده نمی‌کنند، همچنان می‌توانند بدون Branch و بدون Template معتبر باشند. تعیین Branch برای همه Projectها اجباری نمی‌شود.
6. **عدم مدل موازی.** Project و Task فعلی منبع اصلی رفتار و ذخیره‌سازی باقی می‌مانند. Branch و Project Template مفاهیم جدید ساختاری‌اند، اما نباید مدل موازی برای Task یا Project اجرایی بسازند.
## 3. تعاریف موجودیت‌ها
### 3.1 Branch / Center — شعبه یا مرکز
پاسخ «پروژه برای کجا انجام می‌شود؟»؛ مرجع مستقل و ساختاریافته، نه Tag.
حداقل فیلدهای محصولی نسخه اول:
- شناسه پایدار؛
- نام؛
- کد اختیاری؛
- توضیح اختیاری؛
- وضعیت فعال/غیرفعال.
شعبه دارای سابقه Project حذف مخرب نمی‌شود؛ فقط غیرفعال می‌شود. تغییر نام یا وضعیت Branch نباید شناسه و تاریخچه Projectهای آن را از بین ببرد.
### 3.2 Project Template — قالب پروژه
پاسخ «این فرایند معمولاً چگونه انجام می‌شود؟»؛ تعریف قابل استفاده مجدد از فرایند، نه اجرای واقعی.
شامل عنوان، توضیحات و مجموعه Taskهای نمونه است. به Branch یا تاریخ مشخص وابسته نیست، در فهرست Projectهای فعال نمایش داده نمی‌شود و می‌تواند مشاهده، ایجاد، ویرایش، کپی و غیرفعال شود.
فرمان «ذخیره به‌عنوان قالب» از Project موجود یک Template مستقل می‌سازد؛ Project اصلی باقی می‌ماند و ماهیت یا شناسه آن تغییر نمی‌کند.
### 3.3 Project — پروژه اجرایی
اجرای واقعی یک فرایند برای یک Branch و یک دوره مشخص است. می‌تواند Branch و Template مبدأ داشته باشد یا هر دو را نداشته باشد.
عنوان پیشنهادی از ترکیب عنوان Template و نام Branch ساخته می‌شود و کاربر می‌تواند آن را ویرایش کند. دوره، تاریخ شروع و مهلت در صورت نیاز ثبت می‌شوند.
### 3.4 Task — کار اجرایی
اقدام مستقل داخل Project است. در زمان تولید Project از Template، Taskهای نمونه کپی می‌شوند؛ پس از ایجاد، Taskهای Project از Template و Projectهای دیگر مستقل‌اند. تکمیل، حذف یا ویرایش Task در یک اجرا نباید نمونه Template یا Taskهای اجرای دیگر را تغییر دهد.
### 3.5 Tag — برچسب
ویژگی جانبی یا موقت Project یا Task مانند «فوری»، «نیازمند قطعه»، «نیازمند تأیید» یا «بازرسی ویژه». Tag هویت Branch، Template یا دوره را مدل نمی‌کند و جایگزین روابط ساختاری نیست.
## 4. جریان‌های اصلی کاربر
### 4.1 دفترچه شعب
- ایجاد، مشاهده، ویرایش و غیرفعال‌کردن Branch؛
- نمایش تاریخچه Projectهای همان Branch؛
- حفظ تاریخچه با تغییر نام؛
- جلوگیری از حذف مخرب Branch دارای سابقه.
### 4.2 کتابخانه قالب‌ها
- ساخت Template مستقل؛
- ذخیره Project موجود به‌عنوان Template بدون حذف یا تبدیل Project اصلی؛
- مشاهده، ویرایش، کپی و غیرفعال‌کردن Template؛
- اعمال تغییر Template فقط بر اجراهای آینده، نه Projectهای قبلی.
### 4.3 تولید Project از Template
1. انتخاب Template؛
2. انتخاب یک یا چند Branch فعال؛
3. تعیین اختیاری عنوان دوره، تاریخ شروع و مهلت؛
4. پیش‌نمایش تعداد Projectهای قابل ایجاد و نام پیشنهادی هرکدام؛
5. بررسی هشدارهای تکرار؛
6. تأیید آگاهانه کاربر؛
7. ایجاد یک Project مستقل برای هر Branch انتخاب‌شده و کپی Taskهای Template در همان Project.
برای N شعبه انتخاب‌شده، خروجی مورد انتظار N Project مستقل است؛ در مثال پنج Branch، دقیقاً پنج Project مستقل با Taskهای مستقل ساخته می‌شود.
هر Project باید Branch و Template مبدأ را در جزئیات خود به‌صورت قابل مشاهده نشان دهد.
### 4.4 مثال مرجع
Template: «کالیبراسیون یخچال»  
Branchها: مرکز ۵۱۱، ۵۱۲، ۵۱۳، ۵۱۴ و ۵۱۵  
خروجی:
- کالیبراسیون یخچال — مرکز ۵۱۱
- کالیبراسیون یخچال — مرکز ۵۱۲
- کالیبراسیون یخچال — مرکز ۵۱۳
- کالیبراسیون یخچال — مرکز ۵۱۴
- کالیبراسیون یخچال — مرکز ۵۱۵
هر مورد Project مستقل است؛ Taskها فقط در همان Project قابل تغییرند.
## 5. گزارش‌گیری و فیلترها
1. **Branch:** همه Projectهای جاری و تاریخی یک شعبه؛
2. **Template:** همه اجراهای ساخته‌شده از یک Template در شعب مختلف؛
3. **Period:** Projectهای متعلق به یک نوبت/بازه مشخص؛
4. **Status:** شروع‌نشده، در حال انجام، تکمیل‌شده، عقب‌افتاده؛
5. **Tag:** فیلتر مکمل برای برچسب‌هایی مانند نیازمند قطعه یا تأیید.
فیلترها فقط زمانی در محصول فعال معرفی می‌شوند که Query و داده واقعی از آن‌ها پشتیبانی کنند. معنای دقیق «عقب‌افتاده» باید با قواعد وضعیت فعلی Project/Task هم‌راستا شود و از مقدار ساختگی مشتق نشود.
## 6. جلوگیری از تولید تکراری و شکست گروهی
- پیش از تولید گروهی، تعداد و فهرست Projectهای قابل ایجاد نمایش داده شود.
- ترکیب Template + Branch + Period برای تشخیص تکرار بررسی شود.
- اگر برای همین ترکیب Project فعال یا ثبت‌شده وجود دارد، هشدار روشن با امکان مشاهده مورد قبلی نمایش داده شود.
- تکرار فقط پس از تأیید صریح و آگاهانه کاربر مجاز است.
- هویت/نرمال‌سازی Period و سیاست دقیق تشخیص «تکرار» باید پیش از طراحی پایگاه داده تثبیت شود؛ این سند فعلاً قید محصولی را ثبت می‌کند و Constraint دیتابیسی را تجویز نمی‌کند.
- نتیجه تولید برای هر Branch مشخص باشد: ایجادشده، ردشده به‌علت تکرار، یا ناموفق همراه علت. شکست جزئی نباید به‌صورت موفقیت کامل یا نتیجه مبهم گزارش شود.
- پیش از اجرا باید سیاست تراکنش گروهی (همه یا هیچ در برابر نتیجه مستقل هر Branch) در طراحی فنی تعیین و در UI به‌وضوح بازتاب داده شود؛ رفتار ضمنی یا پنهان پذیرفته نیست.

- تغییر یا غیرفعال‌سازی Branch نباید تاریخچه Projectها را حذف یا بازنویسی کند.

- Branch با Tag جایگزین نمی‌شود و Tag نباید هویت ساختاری را حمل کند.
- هیچ قابلیت منسوخ Next Follow-up یا متغیر ساختگی `followUpEnabled` برای مدل‌سازی دوره، وضعیت یا اقدام بعدی بازگردانده نمی‌شود. زمان‌بندی‌های آینده موجود در قرارداد Reminder مستقل باقی می‌مانند.
## 10. معیارهای پذیرش محصول
1. کاربر هر Branch را یک‌بار ثبت کند و بتواند بعداً آن را ویرایش یا غیرفعال کند.
2. کاربر هر فرایند را یک‌بار به‌صورت Template طراحی کند.
3. انتخاب پنج Branch، دقیقاً پنج Project اجرایی مستقل تولید کند.
4. هر Project تمام Taskهای Template را به‌صورت نسخه‌های مستقل داشته باشد.
5. تکمیل/ویرایش Task در یک Project، Projectهای دیگر یا Template را تغییر ندهد.
6. ویرایش Template، Projectهای قبلی را تغییر ندهد.
7. تاریخچه Branch مستقل، کامل و قابل گزارش‌گیری باشد.
8. Projectهای قدیمی بدون Branch/Template همچنان کار کنند.
9. Branch یک موجودیت ساختاری مستقل باشد و با Tag جایگزین نشود.
10. ایجاد تکراری ناخواسته پیش از تأیید کاربر متوقف و هشدار داده شود.
11. شکست گروهی برای هر Branch با نتیجه و علت روشن گزارش شود.
12. هیچ داده، تست یا رفتار تثبیت‌شده فعلی آسیب نبیند.
13. هیچ ارجاع شکسته، `#REF`، رکورد یتیم یا رابطه نامعتبر پس از عملیات/مهاجرت باقی نماند.
14. غیرفعال‌سازی Branch یا Template تاریخچه Projectهای موجود را مخدوش نکند.
15. تولید و گزارش‌گیری بر اساس Branch، Template، Period، Status و Tag با داده واقعی انجام شود.
