# ARVIN FOLLOW-UP AND QUICK ENTRY DECISION

- **Date:** 2026-10-12
- **Status:** ACCEPTED — owner/product decision
- **Scope:** Task follow-up, reminder, full Task form, Quick Entry, Checklist, Calendar display and validation
- **Authority:** This document records the owner command. It supplements `ARVIN_FOLLOW_UP_CONCEPT_DECISION.md`; where older proposals conflict, this newer explicit decision wins.

## 1. Task remains the source of truth

All follow-up and checklist information belongs to the canonical Task. Do not create a parallel Task store, standalone follow-up-time model, duplicate checklist owner, or separate follow-up system.

```text
Task
 ├─ Follow-up
 │   ├─ nextFollowUp
 │   └─ Reminder
 │       └─ reminderDate
 └─ Checklist
```

## 2. Preserve the two independent follow-up concepts

- **`nextFollowUp` — next planned action/review time:** when the user should revisit or act on the topic.
- **`reminderDate` — system reminder time:** when Arvin should notify the user.

Example: for “خرید فرش اتاق”, `nextFollowUp = 25 مهر` means review the purchase on 25 Mehr. `reminderDate = 25 مهر، ساعت 09:00` means notify at 09:00 on 25 Mehr.

Mandatory data rules:
- Never delete, silently migrate, or clear `nextFollowUp`.
- Never copy `nextFollowUp` into `reminderDate` as a fallback.
- Never treat either value as proof that the other exists.
- Preserve both values independently in the model, editor, persistence, JSON, repositories and backup/restore.
- A save/reopen cycle must preserve either field when the other is absent.
- Do not create a “Follow-up Time” concept separate from the Task's follow-up, or a parallel follow-up system.

## 3. Full Task form

- Keep the **«کار پیگیری‌دار»** option.
- Remove the automatically generated follow-up date/time section from the full Task form.
- Enabling “کار پیگیری‌دار” marks the Task as follow-up-enabled; it must not invent a timestamp.
- Do not use `reminderDate` as a substitute for `nextFollowUp`, or vice versa.
- Explicit next-action scheduling belongs to the follow-up controls/flow, not an automatic timestamp generated by the full form.

## 4. Follow-up creation flow

Flow: **Task → افزودن پیگیری → ثبت پیگیری**.

The follow-up entry screen contains:
- Optional follow-up title.
- Follow-up result/notes.
- `nextFollowUp` — next planned action/review time.
- Optional independent next-follow-up reminder (`reminderDate`).

The two date/time controls must be labelled and saved independently. Leaving the reminder empty must not clear a chosen `nextFollowUp`; leaving `nextFollowUp` empty must not clear an explicit reminder.

## 5. Calendar display and notification rules

Calendar display must not hide a planned follow-up merely because no reminder was configured:
- If `reminderDate` exists, display the reminder at its explicit reminder timestamp.
- If `reminderDate` does not exist but `nextFollowUp` exists, display the planned next-follow-up at `nextFollowUp` as a follow-up/action item.
- These are display/projection rules only; they must not mutate stored Task fields.
- A system notification / independently scheduled FollowUp reminder may be created only from an explicit `reminderDate`. Displaying a `nextFollowUp` action item does **not** imply permission to send a notification.
- Every Calendar item must link to its parent Task. Updating an existing linked event must update that event rather than create a duplicate.
- Preserve existing Calendar-origin rules and source identity protections; do not echo imported phone-calendar events back to the provider.

## 6. Quick Entry

Add two compact options:
- **«دارای پیگیری»**
- **«دارای چک‌لیست»**

These options must use the same visual language and icon scale as the existing date, time, repeat and reminder controls. Do not create a large, separate panel.

Preferred balanced arrangement:
- Row 1: Date | Time | Repeat | Reminder
- Row 2: Follow-up enabled | Checklist enabled | More options

An equivalent compact two-row arrangement is acceptable if it preserves clear labels, touch targets, RTL alignment and responsive behavior.

Behavior:
- Enabling **«دارای پیگیری»** expands/activates the follow-up Roll Box.
- Enabling **«دارای چک‌لیست»** expands/activates the checklist Roll Box.
- Keep the main Quick Entry form short. Do not show the full detail editors permanently when their options are disabled.
- Quick Entry and Full Task Form create/edit the same canonical Task.

## 7. Checklist

Checklist is a child capability/data structure of Task: **Task → Checklist**.
- No independent Checklist store or standalone Checklist owner.
- Quick Entry's checklist option activates the Task's checklist Roll Box.
- Preserve checklist data through Task edits and persistence.

## 8. UI and data integrity prohibitions

Do not introduce:
- Independent “Follow-up Time”.
- A second “Next Follow-up” model outside the existing follow-up concept.
- A Reminder that replaces `nextFollowUp`.
- A parallel follow-up system or standalone Checklist store.
- Automatic timestamps generated solely because a Task is marked follow-up-enabled.
- UI fallback logic that writes values into the canonical model.

## 9. Required validation before release

- [ ] `nextFollowUp` is preserved and never silently cleared or migrated.
- [ ] `reminderDate` controls only notification timing.
- [ ] Full Task form retains «کار پیگیری‌دار» and creates no automatic follow-up timestamp.
- [ ] Follow-up creation screen has separate next-action and optional reminder controls.
- [ ] Quick Entry remains compact and visually balanced in Persian RTL and narrow screens.
- [ ] «دارای پیگیری» activates the follow-up Roll Box.
- [ ] «دارای چک‌لیست» activates the checklist Roll Box.
- [ ] Checklist remains owned by Task and survives edit/save/reopen.
- [ ] Calendar shows `reminderDate` when configured; otherwise it shows `nextFollowUp` as an action item when available.
- [ ] Calendar action display does not create a system notification unless `reminderDate` is explicit.
- [ ] Calendar items link to the parent Task and updates do not create duplicate provider events.
- [ ] Both fields survive JSON and backup/restore round trips independently, including one-field-absent cases.
- [ ] Exact-head analysis, tests, build and relevant Calendar/Device Smoke gates pass.
- [ ] Physical-device, RTL/compact-screen and backup/restore acceptance are evidenced separately.

## 10. Execution status

The product decision is accepted. Recording this decision in GitHub does not by itself mean the UI implementation, automated validation, physical-device acceptance or release gate is complete. Track each separately and never claim a gate passed without exact-head evidence.
