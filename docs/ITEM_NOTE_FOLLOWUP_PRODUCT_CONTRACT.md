# قرارداد محصول — مدل نهایی «مورد» / یادداشت / پیگیری

این سند مرجع تصمیم نهایی محصول برای رابطه بین یادداشت ساده و کار پیگیری‌دار است و بر قراردادهای قبلی Note/FollowUp اولویت دارد.

## تصمیم نهایی

آروین نباید برای یک مورد، دو مسیر مستقل `Note` و `Task` داشته باشد که با کپی‌کردن داده به هم متصل شوند.

مدل هدف یک **مورد پایه مشترک (Item)** است:

- عنوان/موضوع
- متن/توضیحات
- تاریخ و ساعت ایجاد
- تاریخ و ساعت قابل ویرایش
- Checklist در صورت نیاز
- دسته‌بندی و Tag
- Reminder اختیاری
- `FollowUps[]` اختیاری

### حالت عادی
مورد جدید در ابتدا مثل یک **یادداشت ساده** رفتار می‌کند.

### فعال‌سازی پیگیری
وقتی کاربر پیگیری را برای همان مورد فعال می‌کند، همان Item به **مورد پیگیری‌دار** تبدیل می‌شود؛ داده‌ها کپی نمی‌شوند و شناسه/متن/تاریخ پایه حفظ می‌شود.

در UI می‌توان Noteهای بدون FollowUp را از موارد دارای FollowUp جدا کرد، اما این جداسازی یک **فیلتر/نمایش** است نه دو مدل داده مستقل.

## پیگیری

هر FollowUp بخشی از تاریخچه همان Item است و حداقل شامل:

- تاریخ و ساعت ثبت‌شده از سیستم به‌صورت پیش‌فرض
- امکان ویرایش تاریخ و ساعت توسط کاربر
- متن/نتیجه پیگیری
- در صورت نیاز زمان پیگیری بعدی

همه سوابق پیگیری باید قابل مشاهده، ویرایش و حذف باشند. آخرین پیگیری همراه ساعت و دقیقه در لیست اصلی نمایش داده می‌شود.

## یادداشت ساده

- موضوع و متن
- درج خودکار تاریخ/ساعت سیستم
- تاریخ/ساعت قابل ویرایش
- ذخیره خودکار
- پس از خروج، نمایش فقط‌خواندنی
- مراجعه بعدی فقط با دکمه ویرایش وارد Edit شود
- فعال/غیرفعال بودن قابلیت/رفتار Notebook از Settings کنترل شود
- Checklist پشتیبانی شود

## زمان Note و Calendar

Timestamp یادداشت فقط metadata همان Item است و **Reminder نیست**.

- Note نباید به Reminder تبدیل شود.
- Note نباید Google Calendar Event بسازد.
- Note نباید Android/system calendar event بسازد.
- Note timestamp نباید صرفاً به‌خاطر وجود تاریخ/ساعت وارد Calendar آروین شود.

Reminder فقط وقتی فعال است که کاربر برای Item یک زمان یادآوری واقعی تعیین کند.

## تقویم و Reminder

تقویم آروین باید فارسی/RTL و هجری شمسی باشد. تجربه UX تقویم و ساعت از `arvin-task-tracker` قابل استفاده است، اما معماری و Source of Truth خود Arvin-clean است.

## فونت

تصمیم نهایی فعلی: **IRANSans / IranSansX(Eco)** به‌عنوان فونت اصلی. فایل فونتی که کاربر قبلاً ارائه کرده منبع مجاز پروژه است. هر تغییر فونت باید با Settings، UI و PDF سازگار بررسی شود.

## سازگاری معماری

قبل از تبدیل کد فعلی به این مدل:

1. `models.Task` و `ArvinTask`/Repositoryهای Legacy مقایسه شوند.
2. Storage فعلی Note و Task بررسی شود.
3. Migration و حفظ داده‌های موجود مشخص شود.
4. FollowUp فعلی به‌عنوان history همان Item بازطراحی/سازگار شود، نه با ساخت مسیر دوم.
5. Calendar/Reminder/Backup/Dropbox compatibility بررسی شود.
6. فقط کمترین تغییر لازم اعمال شود.

## قانون ضد دوباره‌کاری

این سند از این لحظه Source of Truth مدل Note/Task/FollowUp است. قراردادهای قدیمی که Note و Task را دو موجودیت مستقل برای یک مورد فرض می‌کنند superseded هستند و نباید مبنای تغییر جدید قرار گیرند.
