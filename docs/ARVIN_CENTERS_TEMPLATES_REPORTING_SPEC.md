## 3. مدل محصول و رابطه‌ها

### 3.1 موجودیت Center

موجودیت جدید Center دارای حداقل این مشخصات مفهومی است:
- شناسهٔ پایدار و غیرقابل تغییر؛
- نام نمایشی غیرخالی؛
- وضعیت فعال/غیرفعال یا آرشیو برای جلوگیری از انتخاب جدید بدون حذف تاریخچه؛
- زمان ایجاد/به‌روزرسانی در صورت انطباق با الگوی ذخیره‌سازی canonical؛
- نام یکتا پس از نرمال‌سازی در دامنه‌ای که مالک محصول تأیید می‌کند.

Center باید از یک نقطهٔ مدیریت canonical در Settings مدیریت شود. ایجاد، ویرایش نام، فعال/غیرفعال‌سازی و انتخاب Center از همان منبع داده انجام می‌شود. هیچ صفحه‌ای مجاز به نگهداری کاتالوگ مستقل Center نیست.

حذف Center دارای پروژه یا سابقه ممنوع است؛ ابتدا باید آن را غیرفعال/آرشیو کرد. تغییر نام فقط نام نمایشی را تغییر می‌دهد و هویت/ارتباط تاریخی را نمی‌شکند. نام‌های مشابه نباید موجب ادغام خودکار دو شناسه شوند.

### 3.2 رابطه Center و Project

- هر Project جدید می‌تواند به صفر یا یک Center تعلق داشته باشد؛ اتصال Center در ایجاد Projectهای قدیمی الزامی نیست.
- رابطه بر اساس `centerId` پایدار است، نه تطبیق نام.
- Projectهای موجود که Center ندارند با `centerId = null` باقی می‌مانند؛ مرکز جعلی، مهاجرت حدسی یا تغییر تاریخچه ممنوع است.
- انتقال Project به Center دیگر فقط با اقدام صریح کاربر، تأیید اثر بر گزارش‌ها و ثبت امن رابطه مجاز است؛ تاریخچه Taskها و Template origin تغییر نمی‌کند.
- Center غیرفعال برای Projectهای قبلی قابل نمایش و گزارش است، ولی در فهرست انتخاب ساخت Project جدید پیش‌فرض نیست.

### 3.3 Category و Task

قرارداد معنایی نمایش: Center → Project → Category → Task است. با این حال، در مبنای فعلی Category یک مقدار روی Task است و Project فقط Task IDها را عضو می‌کند؛ رابطهٔ مستقل Category→Project وجود ندارد. این سند مجوز ساخت FK یا تغییر اجباری schema برای شبیه‌سازی نمودار نیست.

پیاده‌سازی باید ابتدا معنای فعلی دسته‌های Task را حفظ کند و دسته‌های پروژه‌محور را از طریق عضویت Taskهای همان Project نمایش دهد. دسته‌های پروژه‌محور را از دادهٔ واقعی همان Project استخراج کند. اگر دستهٔ واقعی باید به Project تعلق داشته باشد، تصمیم فنی جداگانه، migration قابل برگشت و تأیید مالک لازم است. تا آن زمان، UI نباید ادعا کند کاتالوگ دسته به‌صورت مستقل زیر هر Project ذخیره شده است.

### 3.4 Task و Tags

- Taskهای ایجادشده برای Projectهای مختلف باید ID مستقل و lifecycle مستقل داشته باشند.
- Tagها از طریق Taskهای canonical اعمال می‌شوند و ممکن است در چند Center/Project دیده شوند.
- هیچ Template یا Center مجاز نیست TaskStore موازی یا Task جایگزین بسازد.

## 4. Project Template Library

### 4.1 تعریف قالب

قالب پروژه یک الگوی قابل استفاده مجدد است، نه Project اجرایی و نه Task فعال. حداقل داده:
- شناسهٔ پایدار Template؛
- نام قابل جست‌وجو و نمایش؛
- فهرست مرتب Template Task definitions؛
- برای هر تعریف: شناسهٔ پایدار درون قالب، عنوان، توضیح و Category/Tag/Checklist فقط در حدی که مدل واقعی Task پشتیبانی و مالک تأیید کرده باشد؛
- وضعیت نگهداری/آرشیو قالب و نسخه یا زمان آخرین تغییر، مطابق طراحی ذخیره‌سازی.

کاربر باید بتواند قالب را ایجاد، مشاهده، ویرایش، تغییر نام، آرشیو و در صورت نداشتن ارجاع فعال حذف کند. حذف قالبی که Project تولیدشده یا سابقهٔ propagation دارد باید مسدود یا به آرشیو تبدیل شود تا گزارش تاریخی از بین نرود.

قالب از Project موجود قابل ساخت است، اما فقط با انتخاب صریح «ذخیره به‌عنوان قالب» و کپی داده‌های ساختاری مجاز. وضعیت انجام، تاریخ‌های اجرایی، Reminderها، FollowUpها، شناسه‌های Task و تاریخچه از Project مبدا به قالب کپی نمی‌شوند.

### 4.2 تولید چند Project برای چند Center

جریان کار:
1. کاربر قالب و یک یا چند Center فعال را انتخاب می‌کند.
2. پیش‌نمایش تعداد Projectها، نام قالب و نام Centerهای مقصد نمایش داده می‌شود.
3. قبل از ثبت، سامانه بررسی می‌کند برای همان Template و Center، Project فعال تکراری وجود نداشته باشد.
4. کاربر عملیات را صریحاً تأیید می‌کند.
5. برای هر Center یک Project مستقل و برای هر Template Task یک Task canonical جدید با ID جدید ساخته و از طریق Project membership به همان Project متصل می‌شود.
6. Project به `templateId` پایدار متصل و نام قالب زمان تولید نیز به‌عنوان snapshot قابل نمایش ذخیره می‌شود.
7. نتیجهٔ هر Center جداگانه نمایش داده می‌شود؛ شکست یک مقصد نباید موجب گزارش موفقیت کل عملیات شود.

هیچ دو Project تولیدشده‌ای نباید Task ID مشترک داشته باشند. تغییر عنوان، توضیح، وضعیت یا تکمیل Task در یک Center نباید در Center دیگر اثر کند. ویرایش بعدی Template نیز به Projectهای قبلی سرایت نمی‌کند.

### 4.3 جلوگیری از تولید تکراری

- تلاش دوباره پس از timeout یا قطع شبکه باید همان عملیات را شناسایی کند؛ retry نباید Project یا Task تکراری بسازد.
- کلید idempotency برای batch تولید و قید یکتایی منطقی برای Template + Center + چرخه باید طراحی شود.
- در نبود مفهوم Cycle در مدل فعلی، ایجاد چرخهٔ جدید یا اجازهٔ Project فعال دوم برای همان Template+Center یک تصمیم حل‌نشده است؛ تا زمان تصمیم، duplicate active ممنوع است.
- کنترل duplicate صرفاً بر نام Project یا نام Center متکی نیست؛ از شناسه‌های پایدار استفاده می‌کند.
- تراکنش/سیاست partial failure باید روشن باشد: نتیجهٔ هر مقصد قابل بازیابی، و retry فقط مقصدهای ناموفق را ادامه دهد.

## 5. افزودن Task جدید به Template در میانهٔ چرخه

هنگامی که کاربر یک Template Task جدید ثبت می‌کند:
1. ابتدا خود Template ذخیره می‌شود.
2. برنامه فهرست Projectهای منتسب به همان Template را بازیابی می‌کند.
3. فقط Projectهای واجد شرایط را با نام Center و Project به کاربر نشان می‌دهد.
4. کاربر می‌تواند هیچ‌کدام، یک مورد یا چند مورد را انتخاب کند؛ انتخاب همه پیش‌فرض نیست.
5. پیش از اعمال، خلاصهٔ «Task جدید + مقصدهای انتخابی» و هشدار عدم تغییر کارهای موجود نمایش داده می‌شود.
6. پس از تأیید، برای هر مقصد یک Task canonical مستقل ساخته و فقط به همان Project افزوده می‌شود.
7. هیچ Task قبلی و هیچ وضعیت تکمیل/آرشیو/توضیح/Reminder/FollowUp تغییر نمی‌کند.

### 5.1 واجد شرایط بودن Project

- Project آرشیوشده با `isArchived == true` قطعاً نامجاز است.
- فقط Projectهایی که با شناسهٔ همان Template منشأ گرفته‌اند بررسی می‌شوند.
- مدل فعلی Project وضعیت «completed» ندارد. بنابراین نباید فیلد status یا completed جدیدی بدون تصمیم ساخته شود و نباید صرفاً فرض شود هر Project غیرآرشیوشده فعال است.
- تعریف دقیق «Project تکمیل‌شده» و رفتار Project خالی باید قبل از فعال کردن propagation نهایی شود. پیشنهاد قابل آزمون برای تصمیم مالک: وضعیت بسته از روی تمام Taskهای غیرحذف‌شدهٔ عضو مشتق شود؛ اگر هیچ Task باز/فعال باقی نمانده باشد، Project برای propagation بسته تلقی شود. این پیشنهاد هنوز تصمیم قطعی نیست.
- تا تعیین سیاست بالا، UI باید eligibility را فقط بر اساس دادهٔ واقعی قابل اثبات اعلام کند و Project مبهم را به‌صورت NOT VERIFIED از انتخاب خودکار کنار بگذارد.

### 5.2 ایمنی، retry و partial failure

- هر Template Task دارای شناسهٔ origin پایدار است.
- رابطهٔ اعمال propagation برای زوج `(templateTaskId, projectId)` باید یکتا باشد.
- اگر Task قبلاً به مقصد اضافه شده باشد، اجرای دوباره no-op امن است.
- اگر batch چند مقصد دارد و بعضی شکست می‌خورند، نتیجه per-project ذخیره/گزارش شود؛ retry فقط مقصدهای ناموفق را هدف بگیرد.
- هر Task جدید در هر Project ID مستقل دارد؛ origin ID فقط برای dedupe و گزارش است.
- Completed/archived Taskهای قبلی هرگز reopen، reset، replace، delete یا mutate نمی‌شوند.
- عملیات باید با lock/transaction متناسب با Store فعلی اجرا شود تا دو تأیید هم‌زمان duplicate تولید نکنند.

## 6. قرارداد پنج فیلتر سراسری

در همهٔ نوارها و انتخاب‌گرهای اصلی که این فیلترها کاربرد دارند، ترتیب ثابت از راست به چپ:
1. **زمان** — گزینهٔ داخلی «همه»
2. **مرکز** — گزینهٔ داخلی «همه مراکز»
3. **پروژه** — گزینهٔ داخلی «همه پروژه‌ها»
4. **دسته** — گزینهٔ داخلی «همه دسته‌ها»
5. **برچسب** — گزینهٔ داخلی «همه برچسب‌ها»

قواعد:
- هیچ چیپ/دکمهٔ مستقل «همه» در نوار فیلتر وجود ندارد.
- انتخاب «همه» فقط state همان بُعد را پاک می‌کند و چهار بُعد دیگر را دست‌نخورده می‌گذارد.
- در حالت بدون فیلتر، رفتار طبیعی فعلی صفحه حفظ می‌شود.
- فیلترها باید بر شناسه و روابط canonical کار کنند؛ تطبیق متن نام مرکز به‌تنهایی کافی نیست.
- ترکیب فیلترها باید مطابق قرارداد فعلی همان صفحه باشد؛ برای معیارهای مستقل، AND semantics حفظ شود مگر سند معتبر موجود رفتار دیگری را تعریف کرده باشد.
- ترتیب RTL باید در Home، انتخاب‌گرهای مرتبط و سطوح فیلتر عمومی یکسان باشد. بخش‌های غیرمرتبط با فیلتر پنج‌گانه نباید به زور پنج گزینه دریافت کنند.

## 7. Report Center — فیلترهای افزوده و حفظ گزارش‌های فعلی

Report Center همان پنج فیلتر عمومی را با همان ترتیب نگه‌دارد و دو کنترل گزارش‌محور اضافه کند:
- **کار:** جست‌وجو/انتخاب Task برای گزارش سطح Task.
- **قالب پروژه:** جست‌وجو/انتخاب بر اساس نام نمایشی Template.

این دو مورد جایگزین یا بخشی از پنج فیلتر عمومی نیستند. تمام فیلترهای فعلی Report Center (از جمله بازهٔ دقیق، اشخاص، وضعیت، نوع، پیگیری، اهمیت، تکرار، چک‌لیست و فیلترهای یادداشت) و انواع گزارش موجود باید حفظ شوند.

### 7.1 هویت Task در گزارش

چون Taskهای هر Project مستقل‌اند، «کار» باید دو حالت را پشتیبانی کند:
- Task مستقل انتخاب‌شده: همان Task ID در همان Project؛
- Template Task origin: تمام occurrenceهای canonical Task که از یک Template Task مشخص تولید شده‌اند، حتی اگر Task ID آن‌ها در Centerهای مختلف متفاوت باشد.

تطبیق صرفاً با عنوان Task مجاز نیست، چون دو Task هم‌نام ممکن است منشأ متفاوت داشته باشند. جست‌وجو نام را نشان می‌دهد اما انتخاب باید شناسهٔ پایدار را حمل کند.

### 7.2 گزارش بر اساس Template

- UI نام انسانی Template را نمایش و جست‌وجو می‌کند.
- Query از `templateId` استفاده می‌کند؛ نام مشابه دو Template نباید نتایج را ادغام کند.
- `templateNameSnapshot` برای نمایش تاریخی زمانی که Template تغییر نام داده یا آرشیو شده استفاده می‌شود.
- پروژه‌های legacy بدون Template با `templateId = null` باقی می‌مانند.
- گزینهٔ قابل فهم «شامل پروژه‌های قدیمی بدون قالب» باید مستقل و پیش‌فرض آن مطابق تصمیم محصول تعیین شود؛ تا تصمیم، عدم شمول صریح و قابل مشاهده باشد.

### 7.3 گزارش بر اساس Center و ترکیب

گزارش‌های لازم:
- یک Center: Projectها و کارهای مرتبط با آن Center؛
- یک Project: Taskها، وضعیت و پیشرفت همان Project؛
- یک Task: occurrence/resultهای آن Task در Projectهای مرتبط؛
- یک Template: تمام Projectهای تولیدشده از آن Template در Centerهای مختلف؛
- ترکیب Center + Template + Task + زمان + Project + Category + Tag و سایر فیلترهای موجود.
