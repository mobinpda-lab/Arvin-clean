# Arvin-clean — Project Documentation Principles v2

**Date:** 2026-08-21

## اصل حاکم
هیچ وضعیت، تصمیم، تغییر معماری، پیشرفت یا نتیجه‌ای نباید فقط بر اساس حافظه، گزارش گفتگو یا حدس ثبت یا اعلام شود.

## چهار منبع اجباری
برای هر تصمیم یا اقدام مهم، این چهار منبع باید تا حد امکان با یکدیگر تطبیق داده شوند:

1. **GitHub واقعی** — Repository، branch، commit، PR، workflow، CI، test، build و merge.
2. **مستندات پروژه در GitHub** — معماری، governance، roadmap، قراردادها، auditها و changelogها.
3. **حافظه و تصمیم‌های تثبیت‌شده پروژه** — سابقه و توافق‌های قبلی برای حفظ continuity.
4. **کد واقعی** — هر زمان رفتار، معماری، migration، storage، test یا قابلیت مورد سؤال است.

GitHub مرجع نهایی برای چیزی است که واقعاً اجرا یا merge شده است. مستندات مرجع تصمیم‌های معماری، governance و roadmap هستند. حافظه فقط continuity است و هرگز بر GitHub فعلی غلبه نمی‌کند.

## فرآیند اجباری
`Audit GitHub → بررسی مستندات → بررسی سابقه تصمیم‌ها → بررسی کد در صورت نیاز → تطبیق → تشخیص اختلاف → تشخیص Gap واقعی → کوچک‌ترین تغییر قابل برگشت → تست focused → Commit → PR → Workflow/CI → Validation دقیق همان commit/ref → به‌روزرسانی مستندات → ادامه توسعه`

## قانون اختلاف
اگر منابع اختلاف داشتند:
- اختلاف ابتدا صریحاً شناسایی شود؛
- GitHub و کد فعلی بررسی شوند؛
- مشخص شود اختلاف تاریخی، مستنداتی یا اجرایی است؛
- سند current-state/handoff مناسب اصلاح شود؛
- اسناد تاریخی بدون دلیل بازنویسی نشوند؛
- از ادامه دادن بر اساس اطلاعات قدیمی جلوگیری شود.

## قانون جلوگیری از دوباره‌کاری
قبل از هر تغییر:
- branchهای موجود بررسی شوند؛
- PRهای باز بررسی شوند؛
- commitهای مرتبط بررسی شوند؛
- workflow/CI مرتبط بررسی شود؛
- مستندات مرتبط خوانده شود؛
- قابلیت و کد موجود بررسی شود.

اگر کاری قبلاً انجام شده، دوباره ساخته نشود. اگر کاری در حال انجام است، parallel implementation تکراری ایجاد نشود.

## اصل توسعه موازی
هدف پروژه: **توسعه موازی + همزمان + سریع، با هدف تولید در چند ساعت به‌جای چند روز.**

کارهای مستقل باید همزمان جلو بروند؛ اما parallelization کور ممنوع است. برای foundation، فایل‌ها و مدل‌های مشترک، ترتیب و مالکیت تغییرات باید مشخص باشد تا conflict، دوباره‌کاری یا شکستن معماری ایجاد نشود.

سرعت هرگز مجوز حذف test، review یا validation نیست.

## قانون گزارش‌دهی
هر گزارش باید بین این موارد تفاوت بگذارد:
- **واقعاً بررسی‌شده**؛
- **واقعاً انجام‌شده**؛
- **در حال انجام**؛
- **باقی‌مانده**؛
- **فرض یا سؤال حل‌نشده**.

Workflow اجرا نشده سبز اعلام نشود. نتیجه CI یک commit هرگز به commit دیگری نسبت داده نشود.

## قانون مستندسازی بعد از تغییر
هر تغییر مهم در architecture، migration، storage/model boundary، roadmap/wave، CI/CD، validation یا governance باید در سند مناسب ثبت شود.

Current state باید در سند canonical/current-state به‌روز شود؛ تاریخچه در اسناد dated update/audit حفظ شود.

## قانون «ادامه آروین»
هر بار کاربر می‌گوید `ادامه آروین`:
1. دسترسی Read/Write و Repository واقعی بررسی شود؛
2. main و آخرین commit/ref بررسی شود؛
3. branchها، PRها و workflowها بررسی شوند؛
4. مستندات مرتبط بررسی شوند؛
5. حافظه/تصمیم‌های قبلی با وضعیت جدید تطبیق داده شوند؛
6. در کار فنی، کد واقعی بررسی شود؛
7. نزدیک‌ترین Gap واقعی انتخاب شود؛
8. در صورت امکان اقدام واقعی انجام شود؛
9. همان commit/ref دقیقاً validation شود؛
10. نتیجه در مستندات مرتبط ثبت شود؛
11. گزارش ساده و غیر فنی ارائه شود.

## اصل نهایی
`GitHub واقعی + مستندات پروژه + حافظه/تصمیم‌های تثبیت‌شده + کد واقعی در صورت نیاز`

سپس:
`بررسی → اقدام → Commit → PR → CI → Validation → مستندسازی → ادامه آروین`

این سند جایگزین تاریخچه قبلی نیست؛ نسخه جدید قرارداد مستندسازی برای ادامه پروژه است.
