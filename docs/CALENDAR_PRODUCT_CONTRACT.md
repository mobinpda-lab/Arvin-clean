# قرارداد محصول تقویم آروین (Calendar Product Contract)

- **نسخه:** 1.1
- **وضعیت:** قرارداد محصول برای بازبینی در PR؛ به‌خودی‌خود تأیید نهایی محصول یا مجوز انتشار نیست.
- **دامنه:** صفحهٔ اصلی، Calendar، Task، Follow-up، یادآور، اعلان، رویداد تقویمی، هویت کارت، جلوگیری از تکرار، زمان، تعامل و آزمون پذیرش.
- **اصل حاکم:** Calendar فقط رویدادهای واجد شرایط را در زمان درست نمایش می‌دهد؛ فهرست همهٔ Taskها و Follow-upها نیست.
- **اصل واژگانی:** در این سند، واژهٔ «یادآور» بدون تعیین نوع نباید به کار رود. هر قاعده باید مشخص کند منظور «یادآور Follow-up»، «یادآور مستقل/عمومی»، «زمان‌بندی Task» یا «اعلانِ ارسال/نمایش» است.
- **اصل شواهد:** نبود شاهد معتبر یعنی `NOT VERIFIED`، نه موفقیت ضمنی.

## 1. واژگان و تعریف‌های لازم‌الاجرا

| اصطلاح | تعریف قراردادی | آیا به‌تنهایی کارت Calendar می‌سازد؟ |
|---|---|---|
| Task / کار | کار یا اقدام کاربر که ممکن است برنامه‌ریزی‌شده یا بدون زمان باشد | فقط اگر زمان برنامه‌ریزی‌شدهٔ معتبر داشته باشد یا رویداد مستقل معتبر دیگری برای آن تعریف شده باشد |
| زمان‌بندی Task | تاریخ/زمانی که خود Task برای انجام برنامه‌ریزی شده است | بله، اگر معتبر باشد و در بازهٔ نمایش قرار بگیرد |
| Follow-up / پیگیری | اطلاعات پیگیری مرتبط با یک Task؛ خودِ پیگیری یک رویداد تقویمی نیست | خیر |
| `nextFollowUp` | مقدار مربوط به پیگیری بعدی؛ یک مقدار داده‌ای است، نه اثبات وجود یادآور ثبت‌شده | خیر |
| Follow-up Reminder / یادآور پیگیری | یادآوری مشخص برای یک Follow-up، که زمان آن صریحاً در `reminderDate` همان Follow-up ثبت شده است | بله، فقط با شروط بخش 5 |
| `reminderDate` | فیلد زمان یادآور پیگیری در مدل Follow-up. این فیلد زمان است، نه یک رکورد مستقل Reminder و نه وضعیت ارسال اعلان | فقط برای همان Follow-up و فقط وقتی معتبر، فعال و داخل بازه باشد |
| Standalone Reminder / یادآور مستقل | رکورد یا منبع یادآور عمومی که مستقل از Follow-up تعریف شده و هویت و زمان خودش را دارد | بله، اگر منبع رسمی، زمان معتبر و وضعیت فعال داشته باشد |
| Notification / اعلان | پیام یا اثر جانبی برای آگاه‌کردن کاربر، مانند اعلان سیستمی. اعلان ممکن است از رویداد دیگری ناشی شود | خیر؛ ارسال یا نمایش اعلان به‌تنهایی رویداد جدید Calendar نمی‌سازد |
| Calendar Event / رویداد تقویمی | رویداد مستقل تقویمی از منبعی که محصول پشتیبانی می‌کند | بله، مطابق قواعد همان منبع |
| Shared Calendar Item / مورد تقویمی اشتراک‌گذاری‌شده | مورد اشتراک‌گذاری‌شده‌ای که طبق قرارداد موجود واقعاً رویداد تقویمی محسوب می‌شود | بله، مطابق قواعد منبع |
| Projection | تبدیل داده‌های منبع به رویدادهای قابل نمایش در Calendar | خودش منبع حقیقت نیست و نباید شرط ورود را تغییر دهد |
| Event identity | هویت پایدار رویداد معنایی در دامنهٔ داده | مبنای یکتایی |
| Card identity | شناسهٔ پایدار کارت UI که یک رویداد معنایی را نمایش می‌دهد | یک رویداد واجد شرایط باید یک کارت متناظر داشته باشد |
| Active range / بازهٔ فعال | محدودهٔ تاریخ/زمانی که Calendar نمایش می‌دهد | فقط رویدادهای متعلق به این بازه نمایش داده می‌شوند |

### 1.1. تمایزهای کلیدی

- **زمان رویداد با اعلان یکی نیست.** رویداد می‌تواند در Calendar نمایش داده شود، چه اعلان دستگاه ارسال شود چه نشود.
- **زمان یادآور با زمان ارسال اعلان یکی نیست.** `reminderDate` زمان برنامه‌ریزی‌شدهٔ یادآوری پیگیری است؛ موفقیت یا شکست ارسال اعلان، شرط وجود کارت Calendar نیست، مگر قرارداد محصول جداگانه‌ای خلاف آن را تصریح کند.
- **زمان‌بندی Task با یادآور Task یکی نیست.** تاریخ انجام Task یک رویداد Task را تعریف می‌کند. اگر منبع محصول یادآور مستقل دیگری برای همان Task داشته باشد، آن یادآور باید هویت و قواعد خودش را داشته باشد.
- **Follow-up با Follow-up Reminder یکی نیست.** پیگیری می‌تواند وجود داشته باشد بی‌آنکه یادآور تقویمی داشته باشد.
- **`nextFollowUp` با `reminderDate` قابل جایگزینی نیست.** مقدار اول به‌تنهایی اثبات نمی‌کند که یادآوری ثبت و فعال شده است.
- این سند وجود یک فیلد یا مدل مستقل برای یادآور عمومی را در کد فرض نمی‌کند؛ چنین منبعی فقط وقتی مشمول قواعد یادآور مستقل است که در معماری فعلی واقعاً وجود داشته باشد.

## 2. تفکیک مسئولیت صفحهٔ اصلی و Calendar

### 2.1. صفحهٔ اصلی

صفحهٔ اصلی نمای عمومی و عملیاتی اطلاعات کاربر است. مطابق طراحی خودش می‌تواند Taskها، Follow-upها، وضعیت کارها و سایر اطلاعات مرتبط را نمایش دهد.

- Follow-up می‌تواند در صفحهٔ اصلی نمایش داده شود، حتی اگر `reminderDate` نداشته باشد.
- نمایش `nextFollowUp` یا اطلاعات پیگیری در صفحهٔ اصلی، مجوز ساخت کارت Calendar نیست.
- حذف کارت Calendar به‌دلیل نبود یادآور نباید رکورد Follow-up را حذف یا از صفحهٔ اصلی پنهان کند.
- اصلاح منطق Calendar نباید منطق ذخیره‌سازی، ویرایش یا نمایش صفحهٔ اصلی را تغییر دهد، مگر علت ریشه‌ای مستقلی اثبات شود.

### 2.2. Calendar

Calendar نمای زمان‌محور رویدادهای واجد شرایط است. منابع مجاز آن عبارت‌اند از:

1. Task دارای تاریخ/زمان برنامه‌ریزی‌شدهٔ معتبر؛
2. Follow-up Reminder دارای `reminderDate` صریح و معتبر؛
3. یادآور مستقل، اگر منبع رسمی آن در محصول وجود دارد و معتبر/فعال است؛
4. رویداد تقویمی پشتیبانی‌شده؛
5. مورد اشتراک‌گذاری‌شده‌ای که طبق قرارداد موجود رویداد تقویمی محسوب می‌شود.

Calendar نباید از تاریخ ایجاد رکورد، تاریخ ویرایش، متن پیگیری، ساعت جاری یا `nextFollowUp` زمان جایگزین بسازد.

### 2.3. جدول جداسازی رفتار

| داده | صفحهٔ اصلی | Calendar |
|---|---|---|
| Task بدون زمان‌بندی | طبق قرارداد صفحهٔ اصلی نمایش داده می‌شود | کارت زمان‌بندی Task ندارد |
| Task با زمان‌بندی معتبر | طبق طراحی صفحهٔ اصلی نمایش داده می‌شود | یک رویداد Task در زمان صحیح |
| Follow-up بدون `reminderDate` | می‌تواند نمایش داده شود | صفر کارت Follow-up Reminder |
| Follow-up با `nextFollowUp` ولی بدون `reminderDate` | منطق پیگیری صفحهٔ اصلی حفظ می‌شود | صفر کارت Follow-up Reminder |
| Follow-up با `reminderDate` معتبر | طبق قرارداد صفحهٔ اصلی | دقیقاً یک کارت Follow-up Reminder |
| یادآور مستقل | طبق طراحی صفحهٔ اصلی، اگر نمایش آن پشتیبانی شود | یک کارت برای رکورد یادآور واجد شرایط |
| اعلان ارسال‌شده یا ارسال‌نشده | طبق رفتار اعلان | به‌تنهایی کارت ایجاد یا حذف نمی‌کند |
| رویداد تقویمی/اشتراک‌گذاری‌شده | فقط اگر صفحهٔ اصلی آن را نمایش دهد | طبق قرارداد منبع تقویم |

**قاعده:** دو صفحه ممکن است دادهٔ پایهٔ مشترک داشته باشند، اما شرط ورود به نمای هر صفحه متفاوت است. هیچ فهرست عمومی یا fallback نباید شرط ورود Calendar را دور بزند.

## 3. قواعد Task و زمان‌بندی Task

1. Task دارای زمان برنامه‌ریزی‌شدهٔ معتبر باید در بازهٔ صحیح Calendar نمایش داده شود.
2. Task بدون زمان‌بندی معتبر، صرفاً به دلیل وجود داشتن، کارت Calendar نمی‌گیرد.
3. تاریخ ایجاد، تاریخ ویرایش یا زمان تکمیل Task جایگزین زمان برنامه‌ریزی‌شده نیست.
4. اگر Task و یک یادآور مستقل دو رویداد معنایی جدا باشند، دو کارت مجاز است؛ در غیر این صورت رویداد واحد نباید دوبار شمرده شود.
5. رفتار Task تکمیل‌شده، لغوشده یا تکرارشونده تابع قرارداد مصوب فعلی است؛ این سند آن رفتار را بدون تصمیم محصول تغییر نمی‌دهد.
6. رخدادهای تکرارشونده باید هویت رخداد مشخص و زمان صحیح داشته باشند؛ رخداد خارج از بازه نباید در بازهٔ فعال ظاهر شود.

## 4. قرارداد یادآور مستقل و اعلان

### 4.1. یادآور مستقل

یادآور مستقل، اگر در محصول به‌صورت منبع واقعی وجود داشته باشد، با Follow-up Reminder متفاوت است.

- باید شناسه، زمان مرجع، وضعیت و منبع رسمی خودش را داشته باشد.
- زمان کارت از فیلد زمانی همان منبع می‌آید.
- یادآور حذف‌شده یا غیرفعال‌شده کارت فعال نمی‌سازد.
- اصلاح Follow-up نباید یادآور مستقل را حذف، تبدیل یا زمان آن را جابه‌جا کند.
- یادآور مستقل نباید با شناسهٔ `reminder-card-followup:...` نمایش داده شود.

### 4.2. اعلان

اعلان یک پیام یا اثر جانبی است، نه الزاماً یک رویداد تقویمی.

- ارسال اعلان برای یک رویداد، کارت دومی ایجاد نمی‌کند.
- شکست ارسال اعلان به‌تنهایی رویداد معتبر Calendar را حذف نمی‌کند.
- دریافت یا بازکردن اعلان، به‌تنهایی رویداد جدید نمی‌سازد.
- زمان ارسال/تحویل اعلان نباید جایگزین زمان Task، زمان رویداد یا `reminderDate` شود.
- اگر محصول روزی بخواهد «اعلان» را به‌عنوان رویداد تقویمی مستقل نمایش دهد، باید نوع داده، شناسه و قواعد پذیرش آن را جداگانه تعریف کند.

## 5. قواعد قطعی Follow-up Reminder

**قاعدهٔ اصلی:** Follow-up یک دادهٔ پیگیری است. تنها Follow-up دارای `reminderDate` صریح، معتبر و فعال می‌تواند یک کارت Follow-up Reminder در Calendar بسازد.

### 5.1. شرط ورود

برای ساخت کارت باید همهٔ موارد زیر برقرار باشد:

1. Follow-up از منبع معتبر بازیابی شده باشد؛
2. شناسهٔ Follow-up معتبر و پایدار باشد؛
3. شناسهٔ Task والد مشخص و ارتباط آن معتبر باشد؛
4. `reminderDate` صریح، قابل تفسیر و معتبر باشد؛
5. یادآور حذف یا غیرفعال نشده باشد، اگر مدل وضعیت چنین حالتی دارد؛
6. زمان در بازهٔ فعال Calendar قرار بگیرد؛
7. رویداد از قبل در مجموعهٔ نهایی با همان هویت معنایی وجود نداشته باشد.

اگر شرط‌های 1 تا 5 برقرار نباشد، رویداد اصلاً واجد شرایط ساخت کارت نیست. اگر فقط شرط بازه برقرار نباشد، رویداد برای بازهٔ فعلی نمایش داده نمی‌شود، اما باید در بازهٔ درست قابل نمایش باشد.

### 5.2. قواعد ممنوع

موارد زیر هرگز به‌تنهایی مجوز ساخت Follow-up Reminder نیستند:

- وجود Follow-up؛
- مقدار پر در `nextFollowUp` بدون `reminderDate`؛
- متن یا توضیح پیگیری؛
- تاریخ ایجاد یا ویرایش Follow-up؛
- تاریخ Task والد؛
- ساعت فعلی سیستم؛
- اعلان ارسال‌شده یا دریافت‌شده؛
- حدس‌زدن `reminderDate` از یک فیلد دیگر؛
- Projection ثانویه، fallback یا cache که شرط اصلی را نادیده بگیرد.

### 5.3. تغییر و حذف

| تغییر داده | نتیجهٔ الزامی در Calendar |
|---|---|
| ایجاد Follow-up بدون `reminderDate` | صفر کارت Follow-up Reminder |
| پر بودن `nextFollowUp` بدون `reminderDate` | صفر کارت Follow-up Reminder |
| ایجاد Follow-up با `reminderDate` معتبر | دقیقاً یک کارت در زمان درست |
| تغییر `reminderDate` | همان رویداد به زمان جدید منتقل شود؛ نسخهٔ قبلی حذف شود |
| خالی/حذف‌شدن `reminderDate` | صفر کارت پس از بازخوانی معتبر |
| حذف Follow-up | کارت آن حذف شود |
| حذف Task والد | هیچ کارت Follow-up Reminder یتیم باقی نماند |
| شکست ارسال اعلان | کارت معتبر فقط به علت شکست اعلان حذف نشود |
| بازخوانی داده | کارت با وضعیت پایدارشده همگام شود |

### 5.4. زمان کارت

زمان نمایشی Follow-up Reminder باید از `reminderDate` همان Follow-up بیاید. نه `nextFollowUp`، نه زمان ایجاد، نه زمان اعلان و نه زمان Task والد مجاز نیست جایگزین آن شود.

### 5.5. شناسهٔ سناریوی Smoke

شناسهٔ مورد انتظار:

`reminder-card-followup:calendar-smoke-task:calendar-smoke-follow-up`

معنای اجزا:

| جزء | معنا |
|---|---|
| `reminder-card-followup` | نوع کارت: Follow-up Reminder |
| `calendar-smoke-task` | شناسهٔ Task والد آزمایشی |
| `calendar-smoke-follow-up` | شناسهٔ Follow-up آزمایشی |

این شناسه برای دادهٔ Smoke است؛ شناسه‌های واقعی باید از شناسه‌های واقعی و پایدار منابع ساخته شوند. آزمون نباید فقط وجود رشته را بررسی کند؛ باید نوع کارت، Task والد، Follow-up و تطبیق زمان با `reminderDate` را نیز بررسی کند.

## 6. هویت رویداد، هویت کارت و جلوگیری از تکرار

### 6.1. سه مفهوم جدا

- **شناسهٔ منبع:** هویت رکورد در منبع اصلی، مانند شناسهٔ Follow-up.
- **هویت رویداد معنایی:** شناسهٔ مفهومی که مشخص می‌کند کدام رویداد محصول نمایش داده می‌شود.
- **شناسهٔ کارت:** شناسهٔ UI برای همان رویداد معنایی.

این شناسه‌ها می‌توانند در پیاده‌سازی به هم نگاشت شوند، اما معناهایشان نباید با هم اشتباه شود. متن کارت، زمان محلی یا موقعیت در فهرست شناسهٔ پایدار نیست.

### 6.2. کلید یکتایی Follow-up Reminder

کلید یکتایی معنایی Follow-up Reminder باید دست‌کم معادل ترکیب زیر باشد:

`(eventType = followupReminder, parentTaskId, followUpId)`

این کلید باید تضمین کند که:
- دو Follow-up متفاوت برای یک Task با هم ادغام نشوند؛
- یک Follow-up به دو Task والد نسبت داده نشود؛
- تغییر زمان همان Follow-up هویت رویداد را عوض نکند؛
- دو مسیر داده برای همان Follow-up Reminder یک رویداد نهایی تولید کنند.

اگر معماری فعلی از کلید دیگری استفاده می‌کند، باید اثبات شود که همین تضمین‌ها را برقرار می‌کند. این قرارداد به‌تنهایی دستور تغییر ساختار پایگاه داده نیست.

### 6.3. قواعد deduplication

1. ابتدا شرط واجد شرایط بودن منبع بررسی شود؛ سپس رویدادهای واجد شرایط براساس هویت معنایی یکتا شوند.
2. Deduplication جایگزین شرط ورود نیست: Follow-up فاقد `reminderDate` نباید ابتدا کارت بگیرد و بعد به امید deduplication حذف شود.
3. دو ورودی با هویت معنایی یکسان، یک رویداد نهایی و حداکثر یک کارت می‌سازند.
4. دو رویداد با هویت‌های مستقل، حتی اگر عنوان یا زمان یکسان داشته باشند، نباید صرفاً بر اساس عنوان/زمان ادغام شوند.
5. زمان، عنوان و متن کارت به‌تنهایی کلید یکتایی نیستند.
6. تغییر زمان رویداد نباید کارت جدید و قدیمی را هم‌زمان باقی بگذارد.
7. حذف یا غیرفعال‌کردن یادآور باید در مجموعهٔ تازه منعکس شود؛ cache یا Projection موازی نباید کارت حذف‌شده را بازگرداند.
8. یک اعلان برای یک رویداد، کارت دوم برای همان رویداد ایجاد نمی‌کند.
9. یادآور مستقل و Follow-up Reminder دو نوع متفاوت‌اند و نباید صرفاً به دلیل زمان یکسان یکی شوند.
10. آزمون باید تعداد تطابق‌ها را دقیق گزارش کند: صفر، یک یا بیشتر از یک.

### 6.4. نتایج مورد انتظار برای یکتایی

| سناریو | تعداد کارت مورد انتظار |

## 8. جریان داده و تشخیص خطا

مراحل پذیرش باید جداگانه قابل بررسی باشند:

1. Persistence: ذخیره در منبع پایدار؛
2. Read-back: بازیابی همان رکورد؛
3. Ingestion: ورود داده به وضعیت برنامه؛
4. Eligibility: بررسی شرط ورود طبق این قرارداد؛
5. Projection: ساخت رویداد از منبع واجد شرایط؛
6. Deduplication: یکتا کردن هویت‌های معنایی؛
7. Range filtering: فیلتر براساس بازه و زمان؛
8. UI render: ساخت کارت با نوع، شناسه و ارتباط صحیح؛
9. Interaction: بازکردن، ویرایش، ذخیره/لغو و بازگشت؛
10. Refresh: همگام‌شدن UI با وضعیت پایدارشده.

موفقیت یک مرحله موفقیت مراحل بعدی را ثابت نمی‌کند. شکست Finder به‌تنهایی منشأ خطا را مشخص نمی‌کند؛ مرحلهٔ شکست باید با شاهد مستقیم تعیین شود.

## 9. زمان، منطقهٔ زمانی و بازه

- زمان منبع، زمان Projection و زمان نمایش باید با قرارداد منطقهٔ زمانی برنامه سازگار باشند.
- برای Follow-up Reminder، زمان مرجع همیشه `reminderDate` است؛ برای Task، زمان برنامه‌ریزی‌شدهٔ Task؛ برای یادآور مستقل، زمان منبع مستقل.
- زمان ارسال اعلان با هیچ‌یک از زمان‌های مرجع بالا جایگزین نمی‌شود.
- آزمون باید ساعت کنترل‌شده داشته باشد و به ساعت واقعی CI وابسته نباشد.
- حد پایین و بالای بازه باید یکنواخت اعمال شوند.
- نیمه‌شب، مرز روز، تغییر ماه/سال و زمان نزدیک مرز بازه باید آزموده شوند.
- رویداد بیرون بازه در بازهٔ فعلی نمایش داده نمی‌شود، اما باید در بازهٔ صحیح قابل نمایش باشد.
- زمان نامعتبر نباید با حدس یا fallback به زمان معتبر تبدیل شود.

## 10. رابط کاربری و چرخهٔ عمر کارت

- Calendar باید فقط کارت‌های حاصل از منابع واجد شرایط و Projection معتبر را نمایش دهد.
- پس از ذخیره، لغو، حذف یا بازگشت از ویرایش، UI باید با وضعیت پایدارشده همگام شود.
- بازسازی Widget، تغییر روز فعال یا بازشدن انتخاب‌گر ساعت نباید کارت معتبر را ناپدید کند.
- تغییر `reminderDate` باید کارت موجود را به‌روز کند، نه اینکه کارت تازه‌ای کنار نسخهٔ قدیمی باقی بگذارد.
- حذف `reminderDate` باید کارت را حذف کند، بدون اینکه Follow-up صفحهٔ اصلی حذف شود.
- اگر کارت در درخت UI موجود ولی خارج از viewport است، باید اسکرول/قابلیت مشاهده بررسی شود؛ این با شکست Projection یکسان نیست.
- آزمون باید هویت، نوع، زمان و ارتباط والد را قبل و بعد از تعامل کنترل کند.

## 11. شواهد تشخیصی و حریم خصوصی

برای هر اجرای پذیرش ثبت شود:
- Run ID، Job ID، وضعیت و پیوند لاگ/Artifact؛
- SHA شاخهٔ PR، SHA ادغام آزمایشی و SHA واقعی Checkout به‌صورت جدا؛
- شاهد Checkout مانند `git rev-parse HEAD`؛
- تعداد رکوردهای بازیابی‌شده و ورودی‌های Projection؛
- شناسهٔ Task و Follow-up آزمایشی؛
- مقدار وجود/عدم وجود `reminderDate` و `nextFollowUp`؛
- تعداد و شناسه‌های رویدادها قبل/بعد از deduplication و فیلتر بازه؛
- زمان منبع، منطقهٔ زمانی، روز فعال و بازهٔ فیلتر؛
- تعداد کارت‌های منطبق و نتیجهٔ تعامل پس از بازگشت.

فقط از دادهٔ ساختگی استفاده شود. Secret، رمز، کلید خصوصی یا دادهٔ شخصی واقعی در لاگ قرار نگیرد. خطای دسترسی به لاگ مانند `BlobNotFound` نه شکست محصول را ثابت می‌کند و نه موفقیت آن را.

## 12. وضعیت‌های پذیرش

| وضعیت | تعریف |
|---|---|
| `PASS` | آزمون روی SHA مشخص موفق شده و شاهد معتبر در دسترس است |
| `FAIL` | شکست با شاهد مستقیم و قابل ردیابی اثبات شده است |
| `IN PROGRESS` | بررسی واقعاً در حال اجراست |
| `NOT VERIFIED` | شواهد کافی، قابل دسترسی یا منطبق با SHA هدف موجود نیست |

موفقیت SQL یا تست واحد Projection به‌تنهایی پذیرش UI یا Device Smoke را ثابت نمی‌کند.

## 13. گیت نهایی Calendar و انتشار

Calendar فقط زمانی پذیرفته می‌شود که:
1. آزمون‌های منابع بخش 7 موفق باشند؛
2. تفاوت Follow-up، Follow-up Reminder، یادآور مستقل و اعلان در کد و آزمون رعایت شده باشد؛
3. آزمون‌های مثبت و منفی `reminderDate` موفق باشند؛
4. هویت کارت و جلوگیری از تکرار در Projection و UI تأیید شود؛
5. زمان، بازه و منطقهٔ زمانی درست باشند؛
6. سایر رویدادها و اشتراک‌گذاری‌ها دچار رگرسیون نشده باشند؛
7. بازگشت از ویرایش در Device Smoke موفق باشد؛
8. Analyze، تست‌های لازم و Device Smoke روی SHA دقیق اصلاح‌شده موفق باشند؛
9. شواهد قابل دسترسی و قابل تطبیق با SHA هدف باشند.

تغییر کد تا پیش از تعیین مرحلهٔ شکست نباید حدسی باشد. هر اصلاح باید هدفمند، کمینه، دارای آزمون رگرسیون و روی شاخهٔ PR انجام شود.

پذیرش Calendar به‌تنهایی مجوز انتشار APK نیست. تا تأیید مستقل شناسهٔ رسمی برنامه، امضا، نصب، سازگاری ارتقا و حفظ داده، وضعیت انتشار باقی می‌ماند:

**`BLOCKED — RELEASE: NO-GO`**

## تصمیم نهایی محصول

«یادآور» اصطلاحی کلی نیست و در کد، آزمون و گزارش باید نوع آن مشخص باشد. زمان‌بندی Task، Follow-up Reminder، یادآور مستقل و اعلان چهار مفهوم متفاوت‌اند. برای Follow-up، فقط `reminderDate` معتبر و صریح مجوز ساخت کارت Calendar است؛ `nextFollowUp`، خود Follow-up یا وضعیت اعلان چنین مجوزی نمی‌دهند. هر رویداد معنایی واجد شرایط فقط یک کارت متناظر دارد.
